# ADR017: The data contract is the source of truth for what an uploaded file means

## Status

Accepted (2026-11-23).

**Builds on:** the per-dataset ODCS contract (#78, ADR011's resolved metadata, `contracts/`), one
typed Parquet per dataset version (#95), declarations of what the user confirmed
(`contracts/declarations.py`), and "Is each row one patient?" (#145).

## Context

An independent review found that the app misread uploaded files before any model ran. Every
component re-guessed the same facts on its own:

| Fact | Who decided it before this ADR |
|---|---|
| Patient key | `VariableTypeDetector.ensure_patient_id` (name list, then uniqueness); `SchemaInferenceEngine._detect_patient_id` (a second name list, `PATIENT_ID_PATTERNS`); `answer_checks.patient_key` (`patient_key_by_name` over the view); `identifier_rules.patient_id_is_row_key` (the name list again); the contract builder (`id_column_from_metadata`) |
| What a row is | the contract's `dataGranularityDescription` ("Several rows per patient_id"), the upload's question, `answer_checks` holds; none named a clinical noun |
| "Is each row one patient?" | `identifier_rules.rows_may_be_patients` over `synthetic_id_metadata` and a third name list (`ID_NAME_TOKENS`) |
| Dates | staging, one format per *value* (a coalesce over a list of formats) |
| Code labels | header codebooks (`variable_types.code_labels`), `extract_codebooks_from_docs` (a regex that stopped labels at the first parenthesis), accepted patches |
| Missing-value codes, units, stated ranges, paired measures | nobody |

The failures that followed: the app's own synthetic `patient_id` declared "one row per patient"
on episode-level rows; keys like `subj`, `patient_ref`, `infant_id`, `case_id`, `study_no`,
`mat_id` missed because only a name list was consulted; `visit_no` treated as an ID; dates read
per row (or not at all for `MM/DD/YY`, `YYYYMMDD` integers, "March 4, 2021"); `99 = not done`
averaged as a score; labels like `1 (first cycle))`; correct visit-level files reported as
`needs_review` because "patient_id: repeated values".

## Decision

1. **One semantics section per dataset version, inside its contract.** The contract's top-level
   custom property `semantics` holds a Pydantic-validated `DatasetSemantics`
   (`contracts/semantics.py`): the grain (a clinical noun, with patient and row counts), the
   patient key with evidence and confidence, the row key, sequence columns ("order within
   patient"), grouping columns (an ID for another role: a mother, a site, a surgeon), app columns
   (`patient_id` copied or hashed by the app, `row_number`: never a patient identifier), and per
   column the logical type, the one date format with a worked example, missing-value codes, a
   stated range, the unit, code labels, timepoint pairing and direction. Open questions that only a
   clinician can settle are recorded in clinical words. Every fact names its source:
   `structure`, `dictionary`, `declared` or `default`. The contract is written once per version
   (immutable, #78), so the semantics are versioned with the data.

2. **One inference pass at upload** (`contracts/inference.py`, with `contracts/dates.py` and
   `contracts/dictionary.py`). It replaces the duplicates listed above; staging's date typing and
   schema inference now call it instead of deciding on their own.

3. **One read API.** `contracts.semantics.semantics_for(data_dir, dataset_id, version)` reads the
   contract and applies the user's declarations; `layer_semantics(layer)` reads the copy a
   semantic layer was built with. Every consumer reads these, and nothing else:

   | Consumer | Reads |
   |---|---|
   | Upload (`user_datasets.save_upload`, `save_table_list`) | runs the pass; `add_id_columns` adds the app ID from the semantics' key |
   | Contract builder / service | ID column, ID rules, grain text, labels, stated ranges, units from the semantics |
   | Upload response and messages (`routes/datasets.py`) | `facts`, `unit_note`, `one_row_per_patient` (only from the open question) |
   | `GET /datasets/{id}/quality` and the Data check panel | `facts` |
   | `GET /datasets/{id}/semantics` | the section itself (for governed and model-written SQL, #154) |
   | Semantic layer (`UploadedDataset._semantic_config`) | patient-key mapping, row-key and askable flags, labels, units, date types |
   | `answer_checks.patient_key` | the layer's semantics (no name list) |
   | `schema_inference.infer_schema` | patient ID column and date columns from the semantics |
   | `autocontext` | entity keys, ID/date/coded types, labels and units |
   | Governed SQL (`sql/catalog.py`, `sql/service.py`) | the ID column from the contract's semantics |
   | Aggregate (`routes/aggregate.py`) | a file whose contract names a patient is never read as estimates |
   | `patient_rows` ("Is each line one patient?") | asked only when the contract holds that open question |

4. **Missing-value codes and date formats are applied where the typed Parquet is written**
   (`apply_semantics`), so every reader (questions, governed SQL, aggregate, previews) sees the
   same values. The raw landing keeps the file as sent.

5. **A user declaration overrides inference** and is stored through `declarations.py` (per
   version). `semantics_for` applies it on read; the contract is never rewritten.

## Applied or asked: the one rule

**A. What may change a number.** A fact that changes a number is applied automatically only
from (1) a structured dictionary entry for that column (its own code list or codebook table:
"99 = not recorded", "777 = Refused" on a measure), (2) an exact structural fact (a dtype, a
unique key, a total row whose whole label is a total label *and* whose count is the sum of the
other lines), or (3) the user's declaration. Everything else is recorded as an open question and
not applied: prose notes and sentences ("Coded fields: 99 = unknown", "ages of 90 or over were
coded as 99"), gap heuristics, total rows found by a label alone or a sum alone, the shape of a
table of groups, and rates told by name. A note that a code stands for a range ("90 or over")
offers that reading: a real, top-coded value.

**B. One hold rule.** Every open question holds, until it is answered, every answer that reads
what it concerns (`contracts.holds.open_question_holds`): a column (`missing_code`, `date_order`,
`date_century`, `censored_value`, `unit_pair`, `unit_missing`), the whole table (`aggregate_unsure`, `total_row`,
`repeated_strata`), or a count of lines (`rows_are_patients`, `person_role`). The question path,
the aggregate path and governed SQL call that one helper on the semantics their data was read
with: the leased layer's own (`LAYER_DECLARED_KEY`), so an answer stored while a question runs
never releases a hold on a layer built before it. A held answer shows the question, never a
number, and a plan confirmation never releases it; governed SQL returns `status: "held"` with the
question ids (its one-row-per-patient confirmation stays its answer to "Is each line one
patient?"). Answers go to `POST /missing-codes`, `/date-readings`, `/one-row-per-patient` (its
"no" is now stored), and `/answers` for the rest.

**Codebooks, exactly.** Only explicit non-response labels apply on their own: "Refused", "Don't
know", "Not asked", or a label that is exactly "Missing" or "Not recorded". Any other label that
may mean not recorded ("9 = Unknown primary (CUP)", "Not applicable") stays a category and is
asked. A range row counts only as the codebook's own "Range of Values"; a clinical reference
range ("12 to 16 | Range of normal values") is not one. Range codes apply only on a measure, when
the label names the edge of its range ("80 = 80 years of age and over" beside 18 to 79); a
category such as "Less than 9th grade" is never one. A unit column is applied only when the
dictionary states it ("Unit of measure for dur") or the user answers `unit_pair`; never for a
rate ("dose_per" = day/week beside "dose_mg"). Every reader then reads the duration in one unit,
the largest the file uses (`contracts.readings`, the stored data unchanged), and the facts name
it; lines with a blank or unknown unit are a `unit_missing` question and hold the column. A
frequency table's total rows (applied or confirmed) are left out of every reader's view, the
semantic layer, governed SQL and the polars reads, by one helper (`readings.total_rows`). When one prose note raises the same
missing-code question on several columns, the app asks it once, and one answer covers them all.
Governed SQL answers a sum of a declared table's count column; the aggregate path scopes column
questions to the columns an estimate question reads, as the other readers do.

**Codebooks.** Codebook tables (a variable header, then "Code or Value | Value Description |
Count | Cumulative", tab, pipe or space separated, with "18 to 79 | Range of Values" rows) are read
as structured entries. On a measure (a range row), explicit non-response codes ("Refused", "Don't know",
"Not asked", exactly "Missing") are missing values. On a coded item they are `nonresponse_codes`: kept in
the stored data and its categories, left out of denominators and averages by every reader, and
the facts say so; the item is typed categorical. Labelled values that stand for a range ("80 =
80 years or older", "666 = less than 1 year") are `censored_codes`: real values, never nulled,
with a `censored_value` question. A text column of time units beside a number ("sleep_dur" and
"sleep_dur_unit") is recorded as `unit_column`. A file with survey weight columns, or a codebook
that mentions sample weights, is a `survey_sample`: its facts say the counts are of the file's
people, and national-estimate questions are declined. An ID the dictionary calls the
respondent/participant sequence number is the person key, so the unit note agrees with it.

## The rule when inference is unsure

When inference is unsure about a fact that would change a number (a missing-value code, a date's
day/month order or century, a key), it records an open question in clinical words and leaves the
values as they are. It never nulls or reinterprets silently: a wrong missing value is the worst
error this app can make.

* A dictionary code is a missing-value code only when its label says the value itself was not
  recorded ("not recorded", "missing", "not available") and the code list keeps at least two coded
  categories. "0 = not done, 1 = done", "1 = refused", "unknown", "not tested" are categories. A
  lone note on a measurement ("PHQ-9 total (0-27). 99 = not done") is a code when it lies outside
  the measurement's stated range.
* An undocumented sentinel (99, 999, -1 ... repeated, far outside the other values, on at least
  0.5 % of lines) is asked ("Does 999 in trop_ng_l mean not recorded?") and never stored as
  missing. Counts, changes and durations (`los_days`, `pain_change`) are not asked. A "yes"
  (`POST /api/datasets/{id}/missing-codes`) is stored as a `MissingCodeDeclaration`; the semantic
  layer's view and governed SQL's view then read the value as missing. The stored Parquet keeps it.
* Day/month order needs at least 3 values, and 10 % of the column, that one order alone reads.
  A two-digit year that reads as a future date, or any two-digit year in a birth or death
  column, asks which century. Both keep the column as text until answered.
* Documented codes on a measurement ("999 = not recorded, 888 = refused") in the column's own
  entry are all missing-value codes, however many. A code stated in prose, for no column or for
  a column a sentence names, is asked about on every column holding it, never applied (A).
* A baby ID unique on every line means each line is one baby, even when a mother ID repeats
  (twins). The baby-or-mother question is asked only when the baby ID repeats too.

## Tables of groups: frequency and estimate tables (with ADR014)

A file whose lines are groups, not patients, is one of two kinds, recorded in the semantics'
`aggregate` section with its count column, its strata and its total rows:

| | Frequency table | Estimate table |
|---|---|---|
| A line | counts cases for one stratum (county x year x sex) | a published value for one stratum: a rate, a percentage, or a count beside total rows |
| "How many" | the SUM of the count column over lines that are not totals | never a sum: the matching line, with each open group at its total ("All", "United States") |
| Recognised by | a count column (whole, non-negative, named cases/deaths/n/...), low-cardinality strata (categories, places, years; never a measure such as age or SBP), or the dictionary saying so | the same, plus rate/percent columns or total rows |

Total rows are recorded per column (`total_levels`) only when the label and the sums agree, and
are then left out of every sum (`contracts.aggregates.count_cases`); a frequency table with
totals is still a frequency table. A label alone ("Overall" whose sums disagree) or a sum alone
(an unlabelled "Statewide", or a rare level that happens to equal two others) is a `total_row`
question. A real category named like a total ("All other causes", "Knee replacement, total") is
one more group. Rate and percentage columns are values whatever their type, by a measure name
(`_rate`, `per_100k`, `_pct`) or the dictionary, never a grouping band (`age_group_per_10y`), and
make the table an estimate table. Time columns (year, week, MMWR week, month, quarter) are strata
whatever their number of values. When more than 20 % of the lines repeat another line's groups
(a survey of banded answers, or stacked copies of one table), the table reading is asked. A table
the structure recognises is recorded (`aggregate`, `source: structure`) and asked about
(`aggregate_unsure`), and is applied only once the user answers "Each row counts cases for a
group (in …)". Governed SQL on a declared table of groups never offers "confirm each row is one
patient": it refuses a count of lines and says to add up the count column.

ADR014's declared public population estimates stay as they are: a declaration (at upload, with
the Electron box, in a `from-url` request, or afterwards with
`POST /api/datasets/{id}/population-estimates`) makes the table an estimate table answered by
ADR014's estimate path. Undeclared tables of groups are now recognised from their structure
(and, for data.cdc.gov links, from the portal's column descriptions, read as the dictionary), so
they no longer go down the patient path; a count question on them is answered from the count
column, said in words, never by counting lines.

## What every reader applies

What the user confirms after upload is applied where data is read, by every reader, through one
definition (`contracts.readings`): the semantic layer's view, governed SQL's view, and the raw
frame the aggregate path reads (`apply_declared`). It covers "999 means not recorded"
(`POST /missing-codes`) and the reading of a date column (`POST /date-readings`: day first or
month first, or the century of a two-digit year). Until a missing-code question is answered, an
answer that reads that column is held (rule B), governed SQL included,
and the quality report lists it as needing an answer. Each answer drops the dataset's cached
layer and query service, so no earlier answer is reused, and the report's line goes at once.

## What is inferred, what is asked

| Fact | Inferred from | Asked when |
|---|---|---|
| Patient key | the dictionary ("subj is the patient identifier", "(patient)"), a key plus a 1..k sequence, an ID named for the patient role (`pt_id`, `subj`, `case_id`, `study_no`), an ID named for a person (`infant_id`, `mat_id`), a repeating ID, a unique ID on a file the dictionary calls one row per patient | nothing names a patient: "Is each line one patient?" (the #145 question, now raised only from the contract); a baby and a mother ID both present: "Is each line one baby or one mother?" |
| Grain | the dictionary ("One row per ED encounter", "Unit of observation: patient"), a sequence, event or date column name (`visit_no`, `ENC_ID`, `sess_date`, `draw_date`) | — (default "record") |
| Sequence | integers numbering 1..k within each patient (≥ 90 % of patients; 98 % for a column not named for numbering) | — |
| Dates | one format that reads every value with a year in 1880–2100; day/month order settled by values above 12; `YYYYMMDD` and Excel serials only for date-named columns or a stated format | both orders read every value differently: "In `col`, does 03/04/21 mean 3 April 2021 or March 4, 2021?"; the column stays text |
| Missing-value codes | the dictionary ("99 = questionnaire not done"); undocumented: one of 99, 999, -1, ... repeated on 2+ rows and far outside the other values (1.5×, or below 0 in a non-negative column, or past a stated range) | — |
| Ranges, units, labels, direction | the dictionary; units also from name suffixes (`_kg`, `_mg_wk`, `_cmH2O`, `_ng_ml`, `_g_cm2`, `_pct`) | — |
| Paired measures | names that differ only by a timepoint (`pre`/`post`, `baseline`/`m6`, `preop`/`12m`) | — |

A real 99-year-old among patients aged up to 98 is a value, not a code; a single 999 is an
entry error reported by the range check, not a code.

## On screen

The facts are said in clinical words (`semantics.describe`): "Each line is one ED encounter; 900
patients (MRN names the patient) over 1,260 lines", "99 in phq9 means not recorded", "Dates like
04/03/21 in draw_date read as 3 April 2021". No SQL, "null", "grain" or "distinct" on screen;
counts are true numbers (ADR015). Date examples are built on a fixed day (3 April 2021), never
from a row.

## Migration

- New uploads: the contract carries `semantics`. Re-uploading the same file gives the same
  version and the same contract (deterministic pass; contracts are immutable).
- Versions stored before this ADR: their contracts have no `semantics`. Every reader (semantic
  layer, upload response, `GET /semantics`, aggregate) goes through
  `contracts.service.version_semantics`, which runs the same one inference pass over the stored
  frame (`stored_semantics`), read-only, with the app columns read from the upload's
  `synthetic_id_metadata`; it is never written over the existing contract. Any other contract
  error fails loudly (HTTP 500), never falls back. A re-upload writes a contract with semantics.
- A visit-level file no longer gets the error-level "one row per identifier" check: repeated
  patient IDs are expected there. A file whose semantics say one row per patient keeps it.
- Removed: `schema_inference.patient_key_by_name`, `PATIENT_KEY_NAMES*`, `PATIENT_ID_PATTERNS`,
  `_detect_patient_id`; `identifier_rules.is_id_name`, `ID_NAME_TOKENS`,
  `repeated_id_columns`; `contracts.service.id_column_from_metadata`,
  `id_source_columns_from_metadata`; `ensure_patient_id`'s own key search (it now calls the pass);
  staging's per-value date coalesce.
- Kept on purpose: the privacy guards that *refuse* a declared estimate table with a person-named
  column (`public_shape.person_id_named`) now use the pass's role names, and still refuse rather
  than pick a key.

## Privacy

`GET /api/datasets/{id}/semantics`, the upload response and `/quality` return patient counts and
evidence sentences. They are shown on this machine as they are (ADR015). Anything that exports or
packages them (a report, a model packet, #154's prompts) must pass through `core.export_boundary`.

## Consequences

- Model-written SQL (#154) reads `GET /datasets/{id}/semantics` or `semantics_for` and must not
  re-derive keys, dates or codes. The API above is stable: new facts are added as optional fields,
  and `schema_version` is bumped for any change in meaning.
- A dictionary in a form the parser does not read (a table in a PDF, a CSV codebook with
  different headings) adds nothing; the structure rules still apply, and the open questions say
  what is left.
