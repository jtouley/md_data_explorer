# ADR013: Contract-governed SQL path

## Status

Proposed (2026-11-13). Base: `origin/main` @ 9ef3fe1. Reference design; the steel thread in [Purpose and steel thread](../../vision/PURPOSE.md) decides which part is built next.

## 0. What exists today (constraints this design keeps)

- **The intent path.** `NLQueryEngine` (`core/nl_query_engine.py`) runs pattern, then embedding, then LLM tiers. It produces `QueryPlan` (`core/query_plan.py:103`, five intents). `QueryService.ask` (`core/query_service.py`) does the locked prepare, an unlocked parse, then a locked `_finish`. `_finish` runs validation, measurement and grouping refusals, `answer_checks` findings, word accounting, `execute_query_plan`, then `format_execution_result`, `present_analysis`.
- **Privacy.** The privacy core is `core/result_presentation.py`:
  - `_suppress_lines(cells, lines, floors)` does primary and secondary suppression for any set of lines with known totals.
  - `suppress_with_exclusions` treats `n_filtered_out` as a hidden cell.
  - Small groups are folded into `OTHER_LABEL`.
  - `MIN_CELL_SIZE = SMALL_CELL_THRESHOLD = 11` (`contracts/config.py`, `nl_query.yaml`).
- **Statistics.** `analysis/compute.py::compute_analysis_by_type(df, context, entity_key)` takes a Polars frame and an `AnalysisContext`. It runs t-test, ANOVA, chi-square, Fisher, logistic regression with ORs and CIs, Kaplan–Meier, log-rank, Cox and correlation. Analysis floors are in `analysis/sample_floors.py`.
- **Contract.** `contracts/builder.py::build_contract` writes one ODCS v3.2.0 file per upload version to `contracts/<upload_id>/<version>.odcs.yaml`, write-once (`store.write_contract`).
  - It covers only the `unified` object.
  - It already carries description, synonyms, unit, `clinicalSemanticType`, enum codebook and the `phi` tag from `ResolvedDatasetMetadata`.
  - Only the DQ checks read it.
  - `contracts/config.py` says "Not bumped yet when a patch is accepted later: the re-contract trigger is deferred."
- **Declarations.** `contracts/declarations.py` stores grain and `LevelMapping` per version in `declarations.json`.
- **AutoContext.** `core/autocontext.py` is built separately, from the alias index and `get_column_metadata`. It is called only from `NLQueryEngine._llm_parse` (around line 2311).
  - It ships `min`, `max` and `top_values` with counts, and does not filter small cells. That is a privacy gap.
  - It crashed on uploads.
- **Metadata patches (ADR011).** `core/metadata_patch.py`, `core/overlay_store.py` and `api/routes/enrichments.py` provide pending, accept, reject, revert and history. Patch `provenance` can be `llm`, `user` or `dictionary`.
- **Documentation (ADR004).** `core/doc_parser.py::extract_context_from_docs` feeds `SchemaInference.parse_dictionary_text`, which returns `DictionaryMetadata` (descriptions, types, valid values, codebooks).
- **Storage.**
  - Each stored table is `parquet/{upload_id}_{table}_{version}.parquet` (`table_parquet_path`).
  - The cohort is `parquet/{upload_id}__cohort_{...}.parquet`.
  - Metadata holds `tables`, `parquet_paths` and `relationships`.
- **Dependencies.** sqlglot 30.31.0 is already in `uv.lock`, pulled in by Ibis 12. DuckDB is 2.0.x.
- **Model.** `nl_query.yaml` sets the default to `llama3.1:8b` with fallback `llama3.2:3b`. This spec plans for 3B: it is the smallest model the app falls back to (`ollama_fallback_model`), so the design has to work at that size. `OllamaClient.generate` posts to `/api/generate`, JSON mode, with no tool calling.

## 1. The contract as the single context

### 1.1 Shape

There is one ODCS v3.2.0 document per (upload_id, dataset_version, revision). There is one `schema[]` object per stored table plus `unified` (the cohort). Top-level `customProperties` hold `uploadId`, `datasetVersion`, `revision`, `minCellSize`, `metadataPatchIds`, `declarations` and `productRef`.

Per table object:

```yaml
- name: labevents
  physicalName: labevents            # view name the SQL path exposes
  logicalType: object
  description: "Laboratory measurements ..."          # doc / patch / user
  dataGranularityDescription: "One row per lab result"
  customProperties:
    - {property: grain, value: event}                 # patient | visit | event | reference
    - {property: patientKey, value: subject_id}       # null for reference tables
    - {property: timeColumn, value: charttime}
    - {property: privacyClass, value: patient_level}  # patient_level | public_aggregate
  relationships:                                      # ODCS v3.1+ relationships
    - {type: foreignKey, from: labevents.subject_id, to: patients.subject_id, customProperties: [{property: cardinality, value: many_to_one}]}
    - {type: foreignKey, from: labevents.hadm_id, to: admissions.hadm_id, customProperties: [{property: cardinality, value: many_to_one}]}
  properties:
    - name: valuenum
      physicalName: valuenum
      logicalType: number
      physicalType: Float64
      businessName: "Lab value"
      description: "..."
      synonyms: [{synonym: result}]
      classification: public|restricted
      tags: [phi]                                      # only when PHI
      enum: [{value: 1, label: "Positive"}]            # documented codebook, never observed values
      customProperties:
        - {property: semanticType, value: measurement} # identifier|demographic|clinical|temporal|outcome|measurement|coded|rate|count|free_text
        - {property: unit, value: "mg/dL"}
        - {property: unitSource, value: dictionary}    # dictionary|patch|user|header|assumed
        - {property: missingTokens, value: ["NA", "-999"]}
        - {property: privacyClass, value: none}        # identifier | phi | public_aggregate | none
        - {property: concept, value: {system: LOINC, code: "2160-0", display: "Creatinine [Mass/volume] in Serum or Plasma"}}
        - {property: weightColumn, value: population}  # for rate columns: required to pool
        - {property: provenance, value: {description: "dictionary:mimic_iv_demo_dictionary.pdf#p4", unit: "patch:p_123"}}
```

The rule from `builder.py` stays: observed values (levels, min and max) are never written into the contract. Samples are computed when the prompt is rendered (see 1.4).

### 1.2 Sources, in precedence order (last wins)

1. **Inference.** dtype; `classify_variable`; header codebooks (`code_labels`); `parse_column_name` units; `MultiTableHandler.classify_tables` grain and keys; `metadata["relationships"]`.
2. **Documentation.** `doc_parser.extract_context_from_docs` feeds `SchemaInference.parse_dictionary_text`, which returns `DictionaryMetadata`. Each entry becomes a `MetadataPatch(provenance="dictionary")`:
   - When the dictionary names the column exactly (normalised), the patch is auto-accepted.
   - When the match is fuzzy, the patch stays PENDING.
   - Either way, documentation flows through the one ADR011 review flow.
3. **Accepted ADR011 patches**, from `llm`, `user` or `dictionary`.
4. **Declarations.** Grain, level merges and units (a new `UnitDeclaration`) from `declarations.json`, copied into `customProperties.declarations`.
5. **Vocabulary (P4).** `contracts/vocabulary.py` matches columns to a curated LOINC subset by name, synonym and unit. Matches are proposed as pending `SET_CONCEPT` patches (a new `PatchOperation`). Accepted concepts add synonyms to the alias index.

### 1.3 Revisions

- **Files.** Revision 0 stays at the existing write-once path. Later revisions go to `contracts/<upload_id>/<dataset_version>/rev-<NNNN>.odcs.yaml` and `version: 1.<N>.0`. The pointer `.../current.json` (`{"revision": N, "sha256": ...}`) is written last through `storage/atomic.py` as the commit point.
- **New module `contracts/revisions.py`:**
  - `ContractChange` is a union: `PatchDecision | DeclarationStored | UserEdit | PortChange`.
  - `apply_change(contract: OpenDataContractStandard, change: ContractChange) -> OpenDataContractStandard` is a pure transform, and is unit-tested.
  - `revise(data_dir, upload_id, dataset_version, change) -> ContractRef` runs under `storage/metadata_lock`.
  - `current_contract(data_dir, upload_id, dataset_version) -> tuple[DatasetContract, ContractRef]`.
- **`ContractRef`** is a frozen dataclass `(upload_id, dataset_version, revision, sha256)`, shown as `"{upload_id}/{version}@1.{rev}.0#{sha12}"`.
- **Triggers.** A new revision comes from:
  - patch accept, reject or revert (`OverlayStore.accept_patch` and the others call `revise`);
  - `QueryService._declare`;
  - a user edit in the review UI;
  - a product-port change.

  This retires the "re-contract trigger is deferred" note.
- **Typed read view.** `contracts/context.py::DatasetContract` is a typed facade over the ODCS model: `tables: dict[str, TableSpec]` and `TableSpec.columns: dict[str, ColumnSpec]`. The gate and the renderer read only this.

### 1.4 Context rendering (replaces AutoContext's inputs)

`contracts/context.py`:

```python
def render_context(contract: DatasetContract, ref: ContractRef, *, purpose: Literal["intent", "sql"],
                   question: str, budget_tokens: int, sampler: SafeSampler | None,
                   tables: Sequence[str] | None = None) -> RenderedContext
@dataclass(frozen=True)
class RenderedContext: text: str; tables: tuple[str, ...]; columns: tuple[str, ...]; tokens: int; ref: ContractRef
```

- **Relevance.** Columns are scored with the existing MiniLM `core/embeddings.py` over businessName, description, synonyms and concept display. The renderer always includes:
  - every key and `timeColumn` of each chosen table;
  - each relationship between chosen tables.
- **Line format, one per column:**
  `labevents.valuenum NUMBER unit=mg/dL type=measurement concept=LOINC:2160-0 "Creatinine" — Lab value. levels: …`
- **Budget.** Counted with tiktoken, as today. Drop order when over budget:
  1. samples;
  2. codebook entries beyond 12;
  3. descriptions truncated to 160 characters;
  4. least-relevant non-key columns.
- **`SafeSampler`** (`contracts/sampling.py`) reads the sandbox connection (section 3):
  - **Categorical, coded or demographic columns with privacyClass `none`.** Levels come from `SELECT col FROM v GROUP BY col HAVING COUNT(DISTINCT key) >= MIN_CELL_SIZE ORDER BY COUNT(DISTINCT key) DESC LIMIT 12`. No counts are sent to the model. Rows are used when the table has no key, and a reference table gets no samples. A column with more than `MAX_GROUP_LEVELS` levels gets "many values" and no samples.
  - **Numeric columns.** p05, p50 and p95 to 2 significant figures, only when at least `5 * MIN_CELL_SIZE` patients have a value. Never min or max.
  - **Dates.** Year of p05 and p95 only.
  - **Identifier, PHI and free-text columns.** No samples, ever.
- **Intent path.** `build_autocontext(...)` keeps its signature as a thin adapter: it calls `render_context(purpose="intent")` and maps the result to the existing `AutoContext` and `ColumnContext`. Its `stats` drop `min`, `max` and counted `top_values`. `_llm_parse` passes the `ContractRef`. This removes the crashing reconstruction path (`_reconstruct_inferred_schema_from_semantic_layer`).
- **Aliases (P4).** `SemanticLayer._build_alias_index` adds contract synonyms and concept displays. The model and the planner then read only the contract.

### 1.5 ODPS product file (P5)

`contracts/<upload_id>/<dataset_version>/product.odps.yaml` follows the Bitol Open Data Product Standard:
- `outputPorts` lists the views the SQL path may query (name, `contractRef`).
- `customProperties` holds `minCellSize`, `sqlProfile: "mdde-sql-1"` (allowlist version), `maxCoreRows: 5000`, `timeoutSeconds: 10`, `maxJoins` (per model tier).

The user can hide a table, such as free-text notes, from questions. Hiding a table removes its port and makes a new revision. Module: `contracts/product.py::current_product(...) -> DataProduct`.

### 1.6 Review in the app

- **API.** Extend `api/routes/enrichments.py`:
  - `GET /datasets/{id}/contract` returns the rendered tables and columns, the provenance of each field, and `ContractRef`.
  - `GET /datasets/{id}/contract/revisions` returns `[{revision, ts, change_summary}]`.
  - `PATCH /datasets/{id}/contract/columns/{table}/{column}` is a user edit. It becomes a `MetadataPatch(provenance="user")` that is accepted on creation.
  - Existing pending, accept, reject and revert are unchanged; each now returns the new `ContractRef`.
- **Electron.** Turn `electron/src/enrichmentPanel.js` into a contract panel: a table, then columns, each with description, unit, type, codebook and privacy. Pending suggestions show inline with Accept and Reject. `patchHistoryPanel.js` shows revisions.

## 2. Static validation (`src/clinical_analytics/sql/validate.py`)

```python
@dataclass(frozen=True)
class ValidatedQuery:
    canonical_sql: str               # sqlglot-generated from the checked AST (what runs)
    ast: sqlglot.exp.Expression
    core: CoreSplit                  # section 4.2
    column_use: ColumnUse            # section 5.1
    views: frozenset[str]
def validate_sql(sql: str, catalog: SqlCatalog, product: DataProduct) -> ValidatedQuery  # raises SqlRefusal(reason: str)
```

Steps, each with a plain-language `SqlRefusal`:

1. **One statement.** `duckdb.extract_statements(sql)` must return exactly 1 statement of `StatementType.SELECT`. DuckDB's own parser is the authority for statement type.
2. **Parse.** `sqlglot.parse_one(sql, dialect="duckdb")`. The root must be `Select`, or `Select` with `With`, or `Union` (constrained in step 8).
   - Forbidden node types anywhere: `Create`, `Insert`, `Update`, `Delete`, `Drop`, `Alter`, `Copy`, `Attach`, `Pragma`, `Set`, `Command`, `Into`, recursive `With`, `Lateral`, and `Table` function calls.
3. **Qualify.** `sqlglot.optimizer.qualify.qualify(ast, schema=catalog.sqlglot_schema(), dialect="duckdb", expand_stars=True, validate_qualify_columns=True)`. Every column resolves to a view.column in the contract, which is the gate's "every column must exist" rule. Unknown tables or tables not in `product.outputPorts` are refused.
4. **Function allowlist.** `sql/functions.py::ALLOWED: dict[str, FunctionRule]`. Anything not listed is refused, including all table functions, `read_*`, `glob`, `query`, `getenv`, `current_setting`, `duckdb_*`, `pragma_*`, `random`, `uuid`, `now` and `current_date`, which break reproducibility.
   - **Aggregates:** count, count(distinct), count_if, sum, avg, median, quantile_cont, min, max, stddev_samp, var_samp, bool_and, bool_or.
   - **Scalars:** arithmetic, round, floor, ceil, abs, ln, exp, sqrt, power, greatest, least, coalesce, nullif, CASE, cast/try_cast, lower, upper, trim, length, substring, contains, starts_with, regexp_matches with a literal pattern of 100 characters or fewer, date_trunc, date_part/extract, year, month, date_diff, date_add with interval literals, make_date, strftime.
   - **Windows:** row_number, rank, dense_rank, lag, lead, first_value, last_value, and sum, count or avg OVER.
   - **Bounded series:** `range` and `generate_series` with literal bounds and at most 1000 values, for calendar spines.
   - **Refused with a pointer:** `corr`, `regr_*`, `covar_*`, `mode`, `list`, `array_agg`, `string_agg`, `histogram`, `arg_min`, `arg_max`, `any_value` and `first` in aggregates.
5. **Privacy-class rules:**
   - Identifier columns may appear only in join conditions, `COUNT(DISTINCT key)`, `PARTITION BY` and `GROUP BY` of non-final blocks. They may never be projected in the final output, grouped at the final block, or compared with a literal. A comparison with a literal would be a question about one patient.
   - PHI columns may appear only inside `year()`, `date_trunc('year'|'month', …)`, `date_diff` or predicates. They may never be projected raw.
6. **Limits.**
   - At most `product.maxJoins` joins: 1 for 3B, 4 for 7–8B.
   - AST size of 400 nodes or fewer.
   - CTE depth of 6 or less.
   - An existing `LIMIT` above 5000 is refused.
7. **Contract gate (P5),** in `contracts/gate.py`, section 5.
8. **Shape.** The core/post split of section 4.2 must succeed, or the query is refused with the reason for that pattern.

`canonical_sql = ast.sql(dialect="duckdb")` after the privacy rewrite. What runs is always text generated from the AST that was checked, never the model's text.

## 3. Sandboxed execution (`sql/sandbox.py`)

```python
class SandboxConnection:
    def __init__(self, catalog: SqlCatalog, *, memory_limit: DuckdbMemoryLimit, threads: int): ...
    def run(self, sql: str, *, timeout_s: float, max_rows: int) -> pl.DataFrame  # raises SqlTimeout, SqlTooManyRows
```

- **Separate connection.** A separate in-memory `duckdb.connect(":memory:", config={...})` per leased dataset version, owned by the `SemanticLayer` lease (`api/layer_cache.py`). It is never the Ibis connection, so the model's SQL can't touch layer state.
- **Connect config:**
  - `enable_external_access=false`;
  - `allowed_paths=[<exact parquet files from metadata["parquet_paths"] and the cohort>]`;
  - `autoinstall_known_extensions=false`, `autoload_known_extensions=false`, `allow_community_extensions=false`, `allow_unsigned_extensions=false`;
  - `memory_limit` set to the layer's share (`CACHED_LAYER_MEMORY_LIMIT`), `threads=DUCKDB_THREADS`;
  - `max_temp_directory_size='0B'`.
- **Catalog views.** `SqlCatalog.from_contract(contract, metadata)` creates views like `CREATE VIEW "labevents" AS SELECT <typed columns, missing tokens to NULL, confirmed LevelMapping merges as CASE> FROM read_parquet(?)`. This gives the SQL path the same merged levels as the intent path's `remap_levels`. Then `SET lock_configuration=true`.
- **Read-only.** Only views exist, the validator admits only SELECT, and external access is off. Even a validator bypass can't read or write files or attach a database. PR4 has a test that runs `read_text('/etc/passwd')`, `COPY` and `ATTACH` directly on the connection and expects errors.
- **Time limit.** A `threading.Timer(timeout_s, con.interrupt)`.
- **Row limit.** The core is wrapped as `SELECT * FROM (<core>) LIMIT max_rows+1`. Getting more than `max_rows` rows is refused ("too many groups to check for small cells").
- **Locking.** Its own lock. It is not the layer's `_con_lock`, so the SQL path never blocks intent questions.

## 4. Privacy on any result shape (`sql/privacy.py`)

### 4.1 Lineage of the patient key

Every block (CTE, subquery or final) is classified by `classify_block(select, catalog) -> BlockKind`:

- **`row_level`**: no GROUP BY or aggregate. The rewriter adds `<view>.<patientKey> AS __pid` to the projection when missing. It is taken from the leftmost patient-bearing source, and a join on declared keys keeps it.
- **`per_patient`**: GROUP BY includes `__pid` or the patient key. `__pid` is kept as a group key, and windows `PARTITION BY __pid` are allowed.
- **`core`**: the one aggregating block whose GROUP BY does not include the patient key. It must read only `row_level` or `per_patient` inputs, or reference tables.
- **`post`**: blocks above the core that read only the core's output.

Refused:
- an aggregation not by patient that feeds another aggregation, which loses lineage and is how averaged rates get pooled;
- two core blocks;
- a patient-bearing input whose `__pid` can't be derived.

### 4.2 Core/post split and companions

`CoreSplit(core_sql, post_sql | None, dims: list[str], measures: list[MeasureSpec])`.

- **Core rewrite.** For the core block with dimensions `D`:
  - Add `COUNT(DISTINCT __pid) AS __n`.
  - For every aggregate node `agg(arg) [FILTER (WHERE f)]` inside output expression `m_i`, add:
    - `COUNT(DISTINCT __pid) FILTER (WHERE f AND arg IS NOT NULL) AS __nn_i_k`, the patients with a value;
    - for indicator arguments only, `COUNT(DISTINCT __pid) FILTER (WHERE f AND arg IS NOT NULL AND arg <> 0 AND arg IS NOT FALSE) AS __nz_i_k`.
  - An argument is an indicator when, statically, it is a boolean, a comparison, or a CASE with constant 0/1 or NULL branches. At runtime, a numeric argument with 2 or fewer distinct values in the core input is also treated as one.
  - `COUNT(*)`, `COUNT(x)`, `SUM(indicator)`, `AVG(indicator)` and `count_if` are additive patient-derived measures.
- **Windows inside the core.** `SUM|COUNT|AVG(agg) OVER (PARTITION BY subset of D)`, used for shares of a total, stay in the core and inherit the companions of their row.
- **Moved to post.** `HAVING`, `ORDER BY`, `LIMIT`, `QUALIFY`, `LAG`, `LEAD` and the rank family are lifted out of the core into post. Applied before suppression, a `HAVING n > 10` would turn the removed groups into one cell that can be worked out from the total.
- **Reference counts**, computed by the runtime in the same sandbox call:
  - `P_all`: distinct patients in the dataset, from cached base counts;
  - `P_core`: distinct `__pid` in the core's input after WHERE;
  - `P_cte[j]`: for each patient-bearing CTE `j` whose pids are a superset of the core input, checked with `NOT EXISTS`. This is the "C. diff positives" cohort a user could count separately.

### 4.3 Suppression (reuses `_suppress_lines`)

`suppress_core(frame, split, refs) -> SuppressedCore(rows, hidden: set[CellKey], folded: bool, notes)`.

- **Cells.**
  - `__n` per row.
  - For additive measures: `nz`, `zeros = nn − nz` and `nulls = __n − nn` per row.
  - Virtual cells, never shown: `outside_all = P_all − P_core` and `outside_j = P_cte[j] − P_core`. They work the way `suppress_with_exclusions` treats `n_filtered_out`.
- **Lines** (sets whose total is treated as known):
  - **(a)** For each count family, all rows plus `outside_all`, which totals `P_all`. The same again with `outside_j` for each reference CTE.
  - **(b)** Within a row, `{nz, zeros, nulls}`, which totals `__n`.
  - **(c)** For two or more dimensions, marginal lines per dimension, as `suppress_count_matrix` builds them.
  - **(d)** When rows overlap (section 6.2), the overlap `Σ__n − P_core` as a virtual cell in line (a).
- **Primary hiding.** A cell is hidden when it is 1–10. Floors: `MIN_GROUP_N` for groups when a tool runs.
- **What a hidden cell does to its row.**
  - Hidden `__n`: the whole row is folded into one `OTHER_LABEL` row whose measures are recomputed by re-running the core with those dimension values merged into one level. If that row is itself 1–10, it is dropped and the note says "groups of fewer than 11 patients are not shown". The labels of small groups are never shown, as in `_fold_rows`.
  - Hidden `nz`, `zeros` or `nulls`: every measure built on that aggregate shows `SECONDARY_SUPPRESSED`.
  - A continuous measure (mean, median, quantile) is shown only if `nn ≥ MIN_CELL_SIZE`.
  - MIN or MAX of a numeric is shown under the same rule. MIN or MAX of a date or timestamp is refused statically unless it is wrapped in `year()` or `date_trunc`.
- **Post stage.** The post SQL runs in the sandbox over the suppressed, folded core registered as `core` (Arrow), with hidden cells as NULL and the `__*` columns dropped. `LAG` over a hidden cell gives NULL, and ranks run over shown rows only, so the post stage can't leak. The note says "ranked among groups of at least 11 patients".

### 4.4 Patterns that can't be enforced (refused, with the text shown)

| Pattern | Why | Refusal |
|---|---|---|
| Final output not aggregated (patient listings, `SELECT *`) | Each row is one patient | "This would list individual patients." |
| Aggregation of aggregates not grouped by patient | Lineage to patients is lost | "Averaging group results hides how many patients each one has. Ask for the measure over patients directly." |
| `UNION`, `INTERSECT` or `EXCEPT` at or above the core; `GROUPING SETS`, `ROLLUP`, `CUBE` | Row overlap can't be bounded statically (a "Both" row) | "Combined or total rows can reveal small groups." Row-level `UNION ALL` of event tables that each carry `__pid` is allowed. |
| Scalar or correlated subqueries in the final SELECT | Hidden extra cohorts | "Write it as a WITH step." |
| `list`, `string_agg`, `array_agg`, `arg_min/max`, `any_value`, `mode` on text | Return a patient's value | Function refused |
| Identifier compared with a literal, or projected | Single patient | "A question about one patient." |
| More than 5000 core groups, or the final group by is the patient key | Every cell is small | "Too many groups to check." |
| Differences across separate questions (`count(A)` then `count(A and p)`) | Not decidable per query | Residual risk, documented in `docs/security/THREAT_MODEL.md`. A later mitigation is a ledger of shown cohort counts, kept per dataset version (not per session: a new chat would reset it), that is checked when a new count differs by one conjunct (section 12, PR 11). |

### 5.1 Using `answer_checks` on SQL

Add `ColumnUse` to `core/answer_checks.py`. Today the checks read a `QueryPlan`; this extracts the column-level inputs they need:

```python
@dataclass(frozen=True)
class ColumnUse:
    view: str
    statistic_columns: tuple[str, ...]   # args of avg/median/sum/stddev/quantile (non-indicator)
    group_columns: tuple[str, ...]       # core GROUP BY dims
    equality_values: tuple[tuple[str, Any], ...]  # col = 'literal', col IN (...)
    limit_columns: tuple[str, ...]       # any predicate column
    counted: Literal["patients", "rows"] | None
    statistic_kind: Literal["describe", "compare"] | None
def column_use_of_plan(plan: QueryPlan) -> ColumnUse            # adapter; existing behaviour
def data_findings(stats: ViewStats, use: ColumnUse, declarations, version, report) -> Findings
```

`ViewStats` is a protocol with `rows()`, `distinct(col)`, `missing(col)`, `value_counts(col)` and `dtype(col)`. `SemanticLayer` implements it for the base view, and `SandboxConnection` implements it per view, with a cache per contract revision. The body of `QueryService._data_findings` moves into `data_findings`. Mapping:

| Existing check | SQL application |
|---|---|
| `grain_of`, `declared_visits`, `grain_hold_reason`, `missing_key_note` | Per patient-bearing view in the core input. A hold applies when the view's grain is undeclared and repeated and a count is `COUNT(*)` or `COUNT(x)` (rows). Tables the contract grains as `event` don't hold, but their counts are labelled "rows (events)". |
| `metric_refusal`, `statistic_refusal` | Every `statistic_columns` entry, so values like "<5" stored as text are refused. |
| `variant_findings` | Group columns and string equality literals. This gives the same hold and `LevelMapping`, and confirming it changes the catalog view and the contract revision. |
| `implausible_sentences` | Statistic and limit columns. |
| `grouped_count_refusal`, `share_refusal`, `varies_within_patient` | Core dims and indicator measures at visit grain. |
| `measurement_grouping_reason`, `grouping_problem` | Core dims, unless the dim is wrapped in a binning expression (`floor(x/10)*10`, `CASE` ranges, `date_trunc`). |
| `missingness_notes`, `report_notes` | All columns read. |
| Word accounting (`unjustified_elements`) | Replaced by `sql/accounting.py::unasked_literals(question, history, ast)`. A WHERE literal or threshold that doesn't appear in the question, the earlier turns or a confirmed synonym is held: "The query limits to `<x>`, which the question did not mention." |

### 5.2 Gate rules

- **Columns exist.** Done by `qualify` against the contract schema.
- **Joins use declared keys.** Every JOIN ON must be a conjunction of equalities that match a contract `relationships` entry, in either direction. Extra conjuncts may only be inequalities or BETWEEN on `temporal` columns (time windows), or literal filters. Cross joins are refused, except to a reference table or a `range` spine.
- **Fan-out.** After a `one_to_many` join, SUM, AVG or COUNT(*) of a column from the "one" side is refused ("counted once per <child row>").
- **Means of codes.** AVG, SUM, MEDIAN or STDDEV of `semanticType ∈ {coded, identifier, demographic-categorical}`, or of a column with `enum`, is refused with the same wording as `numeric_text.statistic_refusal`. A binary 0/1 outcome is allowed and is labelled a share.
- **Pooling rates.** AVG or SUM over `semanticType=rate`, or a name matching `rate|pct|percent|per_?\d+|proportion|ratio` on a reference table, is refused unless it has the form `SUM(rate*w)/SUM(w)` with `w` the contract's `weightColumn`. The refusal shows that rewrite.
- **Overlapping categories.**
  - Static: refuse a dim level literal in `{'all','both','total','overall','any'}` (case-insensitive) inside CASE or WHERE on a group column.
  - Contract and data: when a dimension's documented codebook, or its observed levels from the sampler, include such a level, the gate adds `WHERE col NOT IN (<total levels>)` and says so in the explanation, or holds when the user filtered on it explicitly. Example: CDC "All Sexes".
  - Runtime: when `Σ__n > P_core`, add the overlap line (4.3 d). The note reads "patients appear in more than one row; rows do not add up to the total".
- **Units.**
  - `+`, `-`, comparison, `COALESCE`, `GREATEST` or `UNION` between columns with different contract units is refused unless one side is wrapped in the sandbox macro `convert_unit(x, 'from', 'to')`. The macro is defined from the P4 vocabulary's conversion table.
  - A literal threshold against a column outside `[p01/10, p99*10]` of observed values is held: "check units: `<col>` is recorded in `<unit>`". The percentiles are computed in the sandbox and never shown.
  - Each result column gets a unit:
    - `AVG` or `MEDIAN(x)` gets unit(x);
    - `COUNT(DISTINCT pid)` gets "patients";
    - `COUNT(*)` gets "visits", "events" or "rows" by grain;
    - a ratio gets "per <denominator>".
  - A column alias that says patients when it counts rows is held, using the same unit logic as `query_service._unit_of`.

## 6. Generation, transparency, editing

### 6.1 Generation (`sql/generate.py`)

```python
def generate(question: str, ctx: RenderedContext, examples: list[SqlExample], history: list[SqlTurn],
             client: OllamaClient, feedback: str | None) -> ModelOutput
@dataclass(frozen=True)
class ModelOutput: sql: str | None; tool: ToolCall | None; raw_sha256: str
```

- **Request.** Ollama `/api/generate` with `format` set to a JSON schema (`{"sql": string|null, "tool": {...}|null}`), temperature 0, `num_ctx` 8192, and the timeout `llm_timeout_parse_s`.
- **Examples.** `resources/config/sql_examples.yaml` holds about 40 pairs of question and SQL over a toy patients/visits/labs/meds/micro schema. They cover top-N, rank, trend by year, percent change, pivot with `count_if`, rate per population, a 90-day window join, before/after, first-per-patient windows and follow-up edits. Three are retrieved by embedding similarity.
- **Repair.** Up to 2 retries, feeding back the `SqlRefusal` text, following the `_retry_with_dba_feedback_llm` pattern.
- **3B settings.** `maxJoins=1`, a context budget of 2500 tokens, and SQL only (the tool calls come from routing, 6.4).
- **What a 7–8B model changes.**
  - `maxJoins=4`, with time-window joins and follow-up edits enabled.
  - A 4000-token budget.
  - Tool calls in the same output.
  - Add `ollama_sql_model` to `nl_query.yaml`. Benchmark `qwen2.5-coder:7b` and `qwen2.5-coder:3b` against the llama models, since code-tuned models usually do better at SQL. The benchmark picks the default.

### 6.2 Plain-language plan (`sql/explain.py`)

`explain(q: ValidatedQuery, contract) -> list[str]` is deterministic, built from the AST and contract business names, never from model text. Example:

1. "Start from microbiology results where the test is *C. difficile toxin* and the result is *positive*. Keep each patient's first positive test."
2. "Join prescriptions on patient, for antibiotics started in the 90 days before that test."
3. "Count distinct patients by year of the test. Groups under 11 patients are hidden."

It also lists the rewrites the gate added (total levels excluded, HAVING moved).

### 6.3 Editing and re-running

- `QueryRequest` adds:
  - `mode: Literal["auto","intent","sql"] = "auto"`;
  - `sql: str | None`, a user-edited query that runs through the same `validate_sql`, gate and privacy steps with no model.
- `QueryResult` adds `answer_id: str`, `route: Literal["intent","sql","tool"]` and `sql: SqlPayload | None`, where `SqlPayload` is `{sql: canonical_sql, explanation: list[str], columns: list[ResultColumn], contract_ref: str}`.
- A new route `POST /queries/sql/check` returns validation and explanation without running anything, for live checking in the editor.
- SSE adds `sql_generated` and `sql_checked`.
- Holds reuse the confirm flow: `plan_hash = sha256(canonical_sql + contract_ref + sorted(holds))`.
- Electron gets a new `electron/src/sqlPanel.js`: a collapsible "How this was computed" with the explanation, the SQL in a textarea, and **Run edited query**.

### 6.4 Routing (`core/query_service.py`)

`QueryService.ask` runs the intent path first. That path is the fast one, and its golden suites show 0 WRONG. The new `sql_fallback_eligible(result) -> bool` is true when any of these hold:
- parse failed;
- confidence was below the threshold with no data hold;
- the only hold is the word-accounting hold (`unused_words_reason`);
- the plan was invalid because of an unsupported shape.

Data holds (grain, spellings, implausible values) never fall back, because only the user can settle them. Then `SqlQueryService.ask_sql(...)` runs (`sql/service.py`), with the same three-step locking pattern and `state_generation` re-check.

## 7. Statistics as tools (`sql/tools.py`)

```python
ToolName = Literal["describe", "compare_groups", "find_predictors", "survival", "correlations"]
@dataclass(frozen=True)
class ToolCall: tool: ToolName; cohort_sql: str; outcome: str | None; group: str | None
                predictors: tuple[str, ...] = (); time: str | None = None; event: str | None = None
```

- `cohort_sql` is validated with `validate_sql(..., allow_patient_rows=True)`. That is the only exception to "aggregated output": the frame never leaves the process.
  - It must be `row_level` or `per_patient` with `__pid` unique per row (checked at runtime), or it is held for grain.
  - It may have at most 12 columns, all named in the tool arguments.
- The frame goes to an `AnalysisContext` (intent, primary, grouping, predictors, time, event variables). Then `compute_analysis_by_type(df, context, entity_key="__pid")`, with `analysis["n_filtered_out"] = P_all − P_core` so `suppress_with_exclusions` sees the complement. Then `QueryService._with_findings` (findings from `ColumnUse`), then `present_analysis`.
- All of the existing floors, folding, OR/CI rendering and suppression apply unchanged.
- In SQL, `corr`, `regr_*` and test-like constructs are refused with "use the statistics tool".
- With 3B, the tool is picked by routing: an intent-path parse with intent COMPARE_GROUPS, FIND_PREDICTORS, SURVIVAL or CORRELATIONS whose cohort can't be expressed as filters. The model writes only `cohort_sql`. With 7–8B, the model can return the full `ToolCall`.

## 8. Follow-ups and conversation state

- **`SqlTurn`:** `{question, route, canonical_sql, cohort_sql | None, columns: [name, kind, unit], contract_ref}`. No result values.
- **Storage.** In the session DB: add `Message.payload_json` with an Alembic migration (`api/models/database.py`). `AsyncQueryService.conversation_history` returns `SqlTurn`s for the SQL route.
- **Prompt.** The model sees the last 2 turns' question and SQL and is told to edit the SQL ("now by year", "only women").
- **"Those patients".** The previous `cohort_sql`, or the core input of the last turn, is available as CTE `previous_cohort`. It is re-validated and recomputed, never cached results, so privacy is enforced again.
- **Contract changes.** When `contract_ref` differs from the previous turn, the earlier SQL is re-validated against the new contract. A column that is now missing is refused with the reason.

## 9. Charts (`sql/chart.py`)

- `choose_chart(columns: list[ResultColumn], rows) -> ChartSpec | None` widens `ChartSpec.type` to `bar|line|grouped_bar|heatmap`. It is rule-based:
  - one temporal dim and 1–3 measures: `line`;
  - one categorical dim (at most `MAX_GROUP_LEVELS`) and one measure: `bar`;
  - two dims: `grouped_bar`, or `heatmap` when either has more than 6 levels;
  - otherwise a table.
- A model `chart` hint is accepted only if it names result columns.
- Data comes from presented rows only. Hidden cells are drawn as hatched gaps labelled "hidden (fewer than 11 patients)".
- Histograms are core aggregates over `floor(x/w)*w` bins, so small bins are hidden.
- Electron gets `electron/src/chartView.js` (inline SVG, no external library, which fits the CSP).
- `query_plan.generate_chart_spec` moves here once both paths use it.

## 11. Evaluation

### 11.1 Corpus

`src/clinical_analytics/eval/corpus/corpus.yaml` lists each dataset's `id`, `url`, `sha256`, `license`, `dictionary_url`, `prepare` (a function name) and `tables`. The data is fetched to `<data home>/bench/` by `make bench-corpus-fetch` and is never committed (`check_no_data_files.py`). Datasets:

- **COVID-MS GDSI public sample.** Patient grain, with coded columns and a dictionary.
- **PhysioNet Sepsis 2019.** Training set A, CC-BY 4.0. Hourly PSV files are joined into one long table with `patient_id` taken from the file name; this is the visit/hour grain test.
- **MIMIC-III demo and MIMIC-IV demo (ODbL).** Multi-table ZIP: patients, admissions, prescriptions, microbiologyevents, labevents, d_labitems. These test joins and time windows, including the C. diff question. Because there are 100 patients, many answers must be HELD, which tests privacy.
- **UCI Diabetes 130-US hospitals.** Encounter grain, readmission and rates.
- **UCI Heart Disease (Cleveland).** Coded categoricals, for the means-of-codes guard.
- **A CDC state-year table with `All Sexes` and `All Ages` rows, and a rate per 100k with population.** For example, NCHS provisional COVID-19 deaths by sex, age and state. It tests overlapping categories and pooling. Pin the exact table in the manifest.

### 11.2 Questions and oracles

- Questions live in `tests/eval/corpus/questions/<dataset>.yaml`. Each has `{id, question, capability, follow_up_of?, expect: answer|held, confirm: bool}`. There are about 300 across these capabilities:
  - count, describe, top-N, rank;
  - trend by year, percent change, pivot, rate per population;
  - time-window join, window function, before/after;
  - follow-up chain, statistics tool, arbitrary aggregate;
  - guard probes (grain, overlap, units, pooling, codes);
  - privacy probes: listings, HAVING tricks, LAG next to small cells, complements of a CTE, identifier literals, `read_parquet` and `COPY` injection in the question text;
  - unenforceable patterns, with `expect: held`.
- Oracles are `tests/eval/corpus/oracles/<dataset>.py`: Polars only, written without reading the app's SQL. Each returns `OracleAnswer(frame, unit, cell_patients: dict[CellKey, int])`, so the scorer knows which cells must be hidden.

### 11.3 Harness and scoring

- `eval/corpus/run.py` (`make bench-sql MODEL=llama3.2:3b`). Each run:
  - sets a fresh `CLINICAL_ANALYTICS_DATA_HOME` temporary directory and starts a fresh API process (TestClient on `api.main`), so there are no layer caches, prompt-learning overlays or declarations;
  - uploads every dataset through `POST /datasets/upload`, the real staging path;
  - asks each question chain in a new session;
  - when `confirm: true`, confirms holds the way `eval/headless.ask(confirm=True)` does.
- Grading reads the presented answer (`presented_answer`-style), never raw frames:
  - **RIGHT:** every shown value matches the oracle (counts exact; statistics within 1e-4 relative), labels and unit match, and every oracle cell of 1–10 patients is hidden. Secondary hidden cells are allowed. An `expect: held` question that is held counts as RIGHT.
  - **WRONG:** a shown value differs, the unit or grain is wrong, a non-hidden oracle row is missing, an `expect: held` question is answered, or there is a **LEAK** (a shown cell with 1–10 oracle patients, or a small level's label).
  - **HELD:** held or refused with a reason when `expect: answer`.
  - **ERROR:** exception, timeout, model unavailable, or validation failed after retries.
- Each question runs 3 times at temperature 0 to show nondeterminism. A WRONG in any run counts.
- **Ship bar:**
  - 0 WRONG (including 0 LEAK) for both the 3B model and the chosen 7–8B model;
  - no RIGHT regressions on the intent-expressible subset compared with the intent path alone;
  - the RIGHT rate reported per capability.
- **CI.** The privacy and validator adversarial suites run on the synthetic fixtures (`tests/sql/`). The full benchmark is a manual, release-gate job because it needs Ollama.
