# ADR016: The local model writes the query; every reading it makes is grounded or asked

## Status

Accepted (2026-11-21) for the default question path, in PR #154. Revised 2026-11-23: the path
reads the data contract (ADR017) instead of guessing dataset facts at question time.

**Supersedes:** the keyword matcher (`core/nl_query_engine.py` with its word accounting) as the
default reader of a question. The matcher stays: it answers first when it reads the whole question
cleanly, and it is the whole path when no local model answers. It no longer holds or vetoes a
question the model can answer.

**Builds on:** ADR017 (the contract's semantics are the single source of truth for what a file
means).

Not superseded: the grain and counting-unit rules (ADR013), units and estimate-table traps
(ADR014), true numbers on screen with masking at the export boundary (ADR015), and the local-only
design (the model server must be on this machine; `core/loopback.py`).

## Context

A physician uploads research data and asks plain-English questions. The answer must be right, and
the method must be visible.

Until this change, the question was read by a keyword matcher: every word had to map to a column,
a value or a known phrase, and any word it could not place held the question. Through the API with
llama3.2:3b on `main`:

| set | RIGHT | WRONG | HELD |
|---|---|---|---|
| COVID-MS (15 questions) | 2 | 0 | 13 |
| Fellow case studies (11 blanks) | 0 blanks filled | | |

The matcher was safe and nearly useless: "How many patients were admitted to hospital for
COVID-19 versus not admitted?" was held over the words "admitted", "19", "versus" and "not".

Every open-source text-to-SQL tool that works in practice (Vanna, WrenAI, DB-GPT) uses the same
loop instead: the model writes the query from the schema, descriptions and values; known-good
examples are retrieved as few-shot; errors go back to the model; the SQL is shown.

## Decision

### 1. The model fills a fixed plan; the contract supplies every fact (`src/clinical_analytics/model_query/`)

- `context.py`: the table as the model and the compiler see it, built once per dataset version
  from `semantics_for` (or `layer_semantics` for a version without stored semantics), with the
  user's declarations applied. The grain noun, the patient key (the file's own column, never the
  app's `patient_id` copy), the order column (the contract's sequence column, else its one date
  column), dates, code labels, units, stated ranges, descriptions and open questions all come from
  the contract. The sandbox adds only what values a category holds and a number's range. Nothing
  here reads the question; there is no name list or regex for keys, dates, codes, units or grain.
- `plan.py`: fixed slots, and the reply schema Ollama holds the model to (`format`):
  `answer` (count, share, mean, median, min, max, sum, four tests, list_patients), `count_of`
  (patients, or the contract's records noun), `filters` and `numerator` (each condition a branch
  per column: the column's name as a constant, its operators, and for a category its values in
  the dictionary's words as an enum), `measure`, `group_by` (with `cut_points` for a number,
  `period` for a date), and `which_visit` (any, every, first, last, change). There is no free
  text, no SQL and no self-description (`mapping` and `thought` are gone). The compiler turns a
  valid plan into one SELECT: per-patient any/every (`BOOL_OR`/`BOOL_AND`), first/last
  (`ROW_NUMBER` over the order column), values at baseline / latest recorded / change
  (`arg_min_null`, `arg_max`). A plan it cannot compile raises feedback naming only what the
  compiler supports.
- `examples.py`: few-shot examples on made-up tables whose column names no real or test dataset
  uses; every example shows every slot. The enums make it impossible for an example's names or
  values to appear in an answer.
- `llm.py`: loopback only; temperature 0, fixed seed; the model is kept loaded (`keep_alive`) and
  warmed at app start (`api.serve` sets `CLINICAL_ANALYTICS_MODEL_WARMUP`); a call made before the
  model is known to be warm gets `model_query_cold_timeout_s` (default 900 s; a cold 8B load took
  347 s against the old 300 s limit).

### 2. Checks on what the compiled plan computes (`checks.py`)

The old coverage check read the model's own `mapping` and held good and bad plans alike. The checks
now read the compiled plan and the question through four small, general tables (numbers with their
comparison words, negation words, timepoint words, person nouns) plus the contract.

- **Stated, so applied:** a comparison said with a number ("under 65", "65 or older") sets that
  condition's operator; a timepoint word sets `which_visit` (unless the plan reads that time from
  a sequence or timepoint column); "never" reads every visit; the counted noun (a person, or the
  contract's records noun outside a timepoint phrase) sets `count_of`. A timepoint the question does
  not state is not assumed.
- **Contradicted, so fed back once, then held:** a number of the question the plan does not use; a
  threshold the plan uses that the question does not give; a negation present in one and not the
  other ("is not none" counts as positive); a category label the question names whose column the
  plan does not read.
- **Open, so asked (with choices that re-ask the question):** on a visit-level table, a column the
  plan reads that differs between a patient's visits when the question does not say which visit
  (any, every, first, latest); patients or records when the question names neither; an unanswered
  open question of the contract about a column the plan reads, or about who a line is when counting.
- When the app holds or asks, it logs the answer it would have shown, as numbers only
  (`model_query_held_answer`), so hold quality can be measured. Never a row value or a label.

### 3. The reading card (`card.py`)

Built from templates over the compiled plan and the contract's descriptions and labels: what was
counted and at which visit, the limits in clinical words, the outcome counted, the breakdown, and
the result as "N of M (x%)". No SQL, column names written with `_` or `.`, "null", "grain",
"distinct" or "row"; at most 25 words a line. `card_problems` is the linter; the tests run it over
every card they build. The SQL stays one click away.

### 4. What the matcher still does

The keyword matcher answers first only for a question it fully reads
(`checks.matcher_may_answer`): one record per patient, no number, comparison, negation or timepoint
word, every category label the question names in its plan, and a non-zero, non-empty result.
Everything else goes to the model. With no local model, or `enable_model_queries: false`, the
matcher is the whole path, as before.

## Consequences

- One model call for most questions (about 80-180 s with llama3.1:8b on 4 shared CPU cores); a
  meaning problem or a compile error costs one more.
- `model_query_format` is gone (the plan is the only format); `model_query_cold_timeout_s` is new.
- `model_query/` went from 5,630 lines to about 2,100; see the PR for the counts.
- Tests: `tests/model_query/` (compiler against Polars oracles, checks, card linter, engine loop,
  examples, model call), `tests/core/test_matcher_gate.py`, `tests/api/test_model_query_path.py`,
  and golden replays in `tests/eval/model_query_golden.yaml` (in `make golden`).
