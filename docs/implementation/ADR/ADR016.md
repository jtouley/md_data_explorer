# ADR016: The local model writes the query; every reading it makes is grounded or asked

## Status

Accepted (2026-11-21) for the default question path, in PR #154.

**Supersedes:** the keyword matcher (`core/nl_query_engine.py` with its word accounting) as the
default reader of a question. The matcher stays: it answers first when it reads the whole question
cleanly, and it is the whole path when no local model answers. It no longer holds or vetoes a
question the model can answer.

Not superseded: the grain and counting-unit rules (ADR013), units and estimate-table traps
(ADR014), true numbers on screen with masking at the export boundary (ADR015), and the local-only
design (the model server must be on this machine; `core/loopback.py`).

## Context

A physician uploads research data and asks plain-English questions. The answer must be right, and
the method must be visible.

Until this change, the question was read by a keyword matcher: every word had to map to a column,
a value or a known phrase, and any word it could not place held the question. Through the API with
llama3.2:3b on `main`:

| set | RIGHT | WRONG | HELD |
|---|---|---|---|
| COVID-MS (15 questions) | 2 | 0 | 13 |
| Fellow case studies (11 blanks) | 0 blanks filled | | |

The matcher was safe and nearly useless: "How many patients were admitted to hospital for
COVID-19 versus not admitted?" was held over the words "admitted", "19", "versus" and "not".

Every open-source text-to-SQL tool that works in practice (Vanna, WrenAI, DB-GPT) uses the same
loop instead: the model writes the query from the schema, descriptions and values; known-good
examples are retrieved as few-shot; errors go back to the model; the SQL is shown.

## Decision

### 1. The model writes the query (`src/clinical_analytics/model_query/`)

- `context.py`: the table as the model sees it, built once per dataset version from the SQL
  sandbox: columns, types, the data dictionary's descriptions, every value of a column with at
  most 12, ranges, and the grain (rows are patients, or visits counted by `COUNT(DISTINCT id)`).
  Never a row.
- `examples.py`: few-shot examples retrieved by embedding similarity from
  `resources/config/model_query_examples.yaml`: synthetic questions on made-up tables, never the
  acceptance wording; plus, on a wide table, the columns closest to the question.
- `prompt.py`, `llm.py`: one call to the local Ollama through `OllamaClient` (loopback only, no
  proxies, no redirects), the reply held to a JSON schema, temperature 0 and a fixed seed.
- `plan.py`: the model fills a small plan (`count`, `share`, `mean` ... or a statistical test; a
  `where`, a `group_by`, a share's `numerator`). The app writes the SQL from it, so the counting
  unit, distinct patients on visit rows, a share's denominator, unit conversions and duplicate
  rows are always handled the same, correct way. Values are checked against the listed values
  (spelling repaired), a filter naming every value of a column becomes a breakdown, listing
  individual patients is refused.
- `engine.py`: a failure (a column that does not exist, an engine error, no rows) goes back to
  the model as feedback, at most three attempts.
- `present.py`: counts, shares and summaries become the usual claim and table; statistical tests
  go to `analysis.compute`, never statistics written in SQL.
- Every answer carries the SQL that ran and a one-sentence reading ("Counted distinct patients
  (patient_id) where age_years >= 65 AND result = 'positive', by visit_year."). The window shows
  the reading under the answer and the SQL one click away.

### 2. Plan, not raw SQL

`model_query_format` can be `plan` (default) or `sql` (the model writes the SELECT, the app checks
it). Measured on the same five sets through the API (see the PR): the plan format is the default
because the counting rules are the app's, not the model's. A 3B model that writes
`COUNT(*)` on visit rows reports visits as patients; with the plan it cannot.

### 3. How WRONG is controlled

A wrong number is worse than a refusal. A model's wrong answers are rarely broken SQL. They are
queries that run and answer a slightly different question. A blind test on unseen datasets showed
the same kinds of error with llama3.2:3b and llama3.1:8b, so a bigger model does not fix them; checks
in code do. Each check runs on every compiled plan before any number is shown, and the model cannot
argue past it. When a check fails, the model gets one more try with the failure as feedback. If it
still fails, the user is asked with concrete choices, or told what is missing. The app never makes
a silent pick.

- **A. Counting unit (`units.py`).** What is counted comes from the question's head noun and
  the grain, never from the model.
  - Patient nouns count the patient key distinct on visit rows.
  - Event nouns (visits, admissions, operations, surgeries, cases, sessions, cycles, tests) count
    their own ID column, or the table's distinct rows.
  - A noun the table cannot count as asked is held. It is never counted as another unit.
- **B. Coverage, question to plan (`coverage.py`).** The model returns a `mapping` of question
  phrases to plan elements. Every run of content words must reach the plan. Structural words, unit
  nouns, numbers and the dataset's own name are skipped. A run reaches the plan through:
  - a column's name, its dictionary description, its listed values or decoded labels;
  - a generic clinical synonym, or a value the plan compares with;
  - a mapped phrase whose closeness to the column is checked by sentence-embedding similarity.

  A run that reaches nothing is asked about, naming it and offering the closest columns or "leave
  it out". A count with no filter for "how many women" never passes.
- **C. Links, plan to question (`coverage.py`, `grounding.py`).**
  - Every column the plan reads must be reached from the question in the same verifiable ways.
  - A limit's compared value must be stated; a unit conversion's arithmetic is not checked.
  - A number the question states and the plan never uses is fed back, then held.
  - A concept with no column is held, saying what is missing. It is never answered with other
    columns.
- **D. Ambiguity.** These are asked with concrete choices:
  - a measure stored at two times (`x_baseline`, `x_month6`) when the question names neither;
  - a per-patient summary on visit rows whose value differs between a patient's visits. When the
    value never changes within a patient, it is computed over one value per patient.
  - a share whose event differs between a patient's visits ("ever" or "always");
  - a compound share condition with missing values.
- **E. Dictionary codes (`context.py`).** Code lists in the data dictionary ("1 = male,
  2 = female") are decoded for the codes the column holds. The model sees the labels. Values are
  repaired through them ("women" becomes 2), breakdown tables show them, and the checks above read
  them.
- **The reading and the SQL are shown** with every answer, so a reading the user did not mean is
  visible at once.

Every rule is general: it uses no dataset-specific columns, values or phrasings, and is unit-tested
on made-up tables. The rules shaped by acceptance or blind failures are listed in the PR.

### 4. What the matcher still does

`QueryService.ask` runs the matcher first without its model tier. When it reads the whole question
(no hold, no refusal, no error) its answer is used: it is fast and its readings are exact. Otherwise
the model path answers. With no local model, or `enable_model_queries: false`, the matcher is the
whole path, as before.

## Consequences

- Most questions take one model call: 20-35 s with llama3.2:3b on 4 CPU cores; a doubt or an error
  costs one more call.
- The SQL sandbox now takes its memory share by default (`duckdb_memory_budget` is split over the
  cached layers plus one sandbox).
- Acceptance results with llama3.2:3b are in PR #154. The app's default model (llama3.1:8b) is
  expected to need fewer feedback rounds; the controls above do not depend on the model size.
- Tests: `tests/model_query/`, `tests/api/test_model_query_path.py`, golden samples replaying
  recorded replies without a model (`tests/eval/model_query_golden.yaml`, in `make golden`), and a
  Playwright spec with the model mocked at its HTTP boundary (`electron/tests/e2e/model-query.spec.js`).
