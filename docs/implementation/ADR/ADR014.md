# ADR014: Aggregate-data mode (population estimates)

## Status

Proposed (2026-11-14). Base: `feat/acceptance-corpus-multi` @ 3a42368 (on `main` @ 5a2e5ff). First slice: PR `feat/aggregate-mode`.

**Why its own ADR, not a section of ADR013.** ADR013 designs one path, governed SQL. This mode
changes what a row *is* (an estimate for a group, not a patient), and that change governs both
paths: the intent path today and the SQL gate later. It also records an approved privacy
decision that relaxes two rules for declared datasets. A decision of that weight needs its own
record that ADR013 can point to, instead of being buried in §5.2.

## Problem

CDC tables of causes of death, rates and indicators, CMS hospital C. diff ratios, WHO TB and GBD
extracts hold rows that are estimates. Each row has key dimensions (location, year, age, sex,
cause, measure) and a value, often with lower and upper bounds. On `main`, a real IHME file gave:

- **Pooled overlapping categories.** "Average mx by cause" averaged Male, Female and Both, a state
  and its own counties, and all years, without weights, labelled as n patients: 291 where the
  right figure is about 204–210.
- **A patient test on estimates.** An ANOVA across Male, Female and Both, p<0.001.
- **Patient limits on public data.** At most 20 groups and the small-cell rule blocked a trend by
  year and any question about counties.
- **Packed Excel cells.** IHME's Excel tables hold "401.63 (390.33, 412.62)" in one text cell and
  put years in columns.

## Decision

### 1. Detecting the key dimensions and the value columns (`core/estimates.py`)

`detect_estimate_table(view, rows)` runs once per layer state. Each count is a DuckDB aggregate.

- **Bounds.** A numeric column `x` with `x_lo`/`x_hi`, `x_lower`/`x_upper` or another configured suffix pair (WHO).
  Also standalone `lower`/`upper` or `lowconfidencelimit`/`highconfidencelimit` beside exactly
  one `val`, `mx`, `best`, `datavalue` and the like (GBD, IHME, CDC CDI). Configured in
  `contracts/config.py` (`ESTIMATE_*`).
- **Candidate keys.** Text columns and integer columns named for a key (year, `*_id`, FIPS, ISO).
  Other numeric columns are values; a value is a rate, a count or another value, by name.
- **Key.** The candidates must key every row exactly (`COUNT(DISTINCT key) = rows`, the
  `expect_compound_columns_to_be_unique` check).
  - A column that repeats another row for row is an **alias** (`sex_id` beside `sex`, `FIPS`
    beside `location_name`).
  - A column the others determine is an **attribute**, not a key (`g_whoregion` beside `country`).
    The most varied columns are dropped first, so an ID added at upload never displaces a real key.
- **Not estimates.** A key column with more than rows/2 levels (a record ID), or no interval,
  rate or total level anywhere. Patient-level files fall out here; the corpus check found no
  false positive among the patient sets.
- **Totals (parents).** A level is the total of the others in its column when:
  - it is named as one ("Both", "All Sexes", "All ages", "United States", "Overall", "Entire
    Network", WHO "a" beside "m"/"f");
  - it is an age band containing another band present ("65+" beside "65-74"), only in a column
    named for age;
  - it is a non-county level in a column where the other levels are counties (the state row
    beside its counties).

  The single total of all other levels, when there is one, is the column's `top`.

Detection only adds checks. It never relaxes a rule (see 7).

### 2. Totals are parents, never peers

- **Grouping by a dimension.** Its total levels are left out of the groups, and the answer says
  so: "Both is the total of the other sex values, so it is left out."
- **Counties.** "Which Colorado county …" ranks the counties, not the state row.
- **A dimension the question leaves open.** It is never averaged across (see 3).

### 3. Holding a question when a dimension isn't fixed (`check_plan`)

After the plan's limits, each key dimension that is not grouped must have one level left.

- **Grounding first.** `ground_plan` reads only the question's words and the published levels.
  Years: one pins, several with "from/between/change" become groups, "by year"/"trend" groups.
  Level phrases: plural-insensitive, longest match ("cardiovascular disease" names
  "Cardiovascular diseases"). The question's exact value-column name wins over a fuzzy parse.
- **Hold.** If every open dimension has a `top`, the question is held: "The question doesn't fix
  sex (Both, Female, Male; Both is the total). Confirm to use sex = Both and save that choice for
  this dataset, or name another value."
- **Confirming saves the choice.** It is stored as `DimensionChoice` in `declarations.json` (per
  dataset version), which is the contract's declarations section (ADR013 §1.2 source 4). It is
  an approved plan change: later answers use it and say "Uses sex = Both, the choice saved for
  this dataset."
- **Refusal.** If any open dimension has no total (year, cause), the question is refused and the
  refusal names what to fix. No confirmation can release it.
- **Word accounting.** Forward accounting still runs on the words left after the estimate
  vocabulary (`ESTIMATE_QUESTION_WORDS`). Reverse accounting is replaced by the answer naming
  every level it is for ("mx for location_name = Colorado, cause_name = …, sex = Both,
  year_id = 2014").

### 4. Never pooling rates without weights

- A mean, median or sum across estimate rows is never computed. A question whose limits leave
  more than one row per group is held or refused (3).
- Grouping by an attribute (WHO region) is refused: "g_whoregion does not identify the
  estimates, so a breakdown by it would mix several estimates in each group."
- A share of rows is refused: a share of rows is not a share of people.
- **Later.** A weighted pool `SUM(rate*w)/SUM(w)` with the contract's `weightColumn`
  (population), per ADR013 §5.2, once a population column is declared. Not in this PR.

### 5. Intervals carried to the answer

- **Value column.** It keeps its file name. Every row shows `lower` and `upper`, and the claim
  writes "209.52 (203.89 to 215.40)".
- **Interval check.** `lower ≤ value ≤ upper` is checked per shown row (the GX
  `expect_column_pair_values_a_to_be_greater_than_b` pair, `or_equal=True`). A row that fails, or
  has one bound missing, shows no interval and is named in a note.
- **Comparing two estimates.** "Their intervals don't overlap, so the estimates differ"; or
  "Their intervals overlap, so these estimates are not shown to differ"; or, without intervals,
  "can't be judged".
- **Ranking.** The top group, and the groups whose intervals overlap it: "its rank among them is
  uncertain".
- **Trends.** First and last points in the claim, all points in the table.

### 6. Patient-level tests off

On an estimate table:

- COMPARE_GROUPS compares intervals, never ANOVA or a t-test, and says "no significance test is
  run on them".
- FIND_PREDICTORS, CORRELATIONS and SURVIVAL are refused.
- COUNT counts rows and says "rows". No column is a patient key, so an ID synthesized at upload
  never makes a row a patient.

### 7. The declaration flow (approved privacy decision)

- **The mark.** At upload, the person ticks "Public population estimates – no patient-level data"
  (`POST /datasets/upload`, form field `population_estimates=true`). The statement they agree to:
  "Every row is a published estimate for a place, period or group (for example a rate per
  100,000 with its interval), and no row describes a single patient."
- **Where it is stored.**
  - Per dataset in `declarations.json` (`PopulationEstimatesDeclaration`).
  - In the contract's `customProperties` (`privacyClass: public_aggregate`,
    `populationEstimates`).
  - Echoed in the upload response.
- **Declared estimate tables.**
  - The 20-group limit is lifted.
  - The small-cell rule does not apply to estimated rates.
  - It still applies to any count column: values 1–10 are hidden ("Counts from 1 to 10 are
    hidden.").
- **Undeclared estimate tables.** Statistic questions are refused, because each row would be one
  person and a small cell: "…It wasn't marked 'Public population estimates – no patient-level
  data' at upload… upload it again with that box ticked." Hospital extracts keep the full rules,
  and detection alone never relaxes anything.
- **UI.** The upload checkbox in Electron is the next PR. The API and the harness carry the mark
  now.

### 8. Packed cells and years as columns (`storage/staging.py`)

- **Packed cells.** A text column whose every non-empty cell is "v (lo, hi)" becomes `x`,
  `x lower` and `x upper`. These pair as bounds (1).
- **Years as columns.** Three or more packed columns whose headers each name one year ("Mortality
  Rate, 1980*") are unpivoted to `year` plus the value columns, before typing.
- **Everything else.** Other columns are untouched.

### 9. Fit with steps 3–4 of the steel thread

- **Step 3 (contract as context).** The contract now carries `privacyClass: public_aggregate`.
  Next: the estimate key, aliases, attributes, totals and bounds as `customProperties` on the
  table object (`grain: estimate`, `keyColumns`, `totalLevels`, `boundsOf`), rendered into the
  model's context (#107), so the model sees "one row per location × year × sex; Both is the
  total" and stops writing pooled plans.
- **Step 4 (governed SQL).**
  - `contracts/gate.py` reuses `check_plan`'s rules on the SQL AST. An aggregate over a value
    column with an open key dimension is refused (§5.2 "Pooling rates"). A WHERE that keeps a
    total beside its parts is rewritten or held (§5.2 "Overlapping categories").
  - The privacy rewrite of §4 is skipped only for `public_aggregate` tables, and only for
    non-count value columns.
- **Order.** Both steps read the same detection result, so intent and SQL answers agree.

## Consequences

- Correct answers or correct holds replace pooled answers on population files. The WHO TB
  acceptance set moves from 3 to 7 RIGHT with 0 WRONG and no model. The 8 IHME probes on
  synthetic files of the same shape answer or hold as specified.
- **Residual: counts.** Count tables with stacked grains (CDC provisional COVID: by total, by year
  and by month in one file) are detected, and their totals are left out of groups. Summing counts
  across rows is not offered.
- **Residual: long format.** Long-format files that put a value and its bounds in separate rows
  (CMS HAI `HAI_6_SIR`/`_CILOWER`) are not detected yet. They need a pivot by measure and are
  answered under the full rules.
- **Residual: weights.** No weighted pooling until a weight column is declared.
