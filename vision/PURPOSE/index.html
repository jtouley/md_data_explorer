    Purpose and steel thread

    This page says what the product is for and the order in which it gets built. It is the current direction. The master plan lists older plans and the Electron cutover.

    Purpose

    This is a local data analyst for anyone in medicine who has a dataset and a question: medical students, residents, fellows, attendings and faculty, in any specialty.

    • Any question. They ask in their own words, about anything a capable data tool such as TextQL could answer.
    • Right answer, method shown. They get the right answer and see the method, from a local model (Ollama).
    • Privacy. Data never leaves the machine. No answer shows a count of 1–10 patients, or a count that can be worked out from that answer and its filters in any combination. See What privacy does not cover yet.
    • Any data. Public datasets, registry exports, and hospital extracts with their dictionaries.

    Use cases such as the ID-fellow research guide are examples, not the scope. The product is not narrowed to one specialty, one workflow or a fixed list of question types.

    What "works" means

    Right answers on real public datasets, through the real upload API, with the local model running, from a fresh app state. Passing unit tests, a green CI or a safe hold do not count as "works".

    The acceptance table reports two rates and never adds them together:

    • Answered right: questions that expect an answer and got the right one. This is the usefulness number.
    • Correctly held: questions that must be refused (a patient listing, for example) and were. This is a safety number, with WRONG and LEAK.

    Steel thread, in order

    The first unfinished step is the one being worked on. Work that does not move it waits, except for the privacy, security and data-loss fixes described under Merge gate.

    1. The model tier runs on uploaded datasets. This came with #101.
    2. An acceptance harness on COVID-MS (GDSI, PhysioNet). It reports RIGHT, WRONG, HELD, ERROR and LEAK for each question, which gives the baseline.
    3. It came with #104: make accept DATASET=covid_ms MODEL=....
    4. It reuses presented_answer from src/clinical_analytics/eval/headless.py and the presented-answer graders in tests/eval/test_presented_answers.py.
    5. Baseline: of 14 questions that expect an answer, 1 is answered right and 13 are held. The one question that must be held is held. 0 WRONG, 0 LEAK.
    6. The data contract becomes the model's only context: dictionary, codebooks, units, grain and keys.
    7. Done when the COVID-MS answered-right count rises with the dictionary uploaded, at 0 WRONG and 0 LEAK, on the held-out questions. Better context alone does not count.
    8. The contract feeds word accounting. Its synonyms and descriptions count a question's words as used ("MS type" is in ms_type2's description). This moves forward from ADR013's PR 2.
    9. A hold offers a choice of column, not "rephrase". It lists the 2–3 contract columns that best match the word, plus "none of these". The choice is saved to the contract as a user synonym, so each word is asked about once per dataset.
    10. A confirmation re-runs the stored plan. It never asks the model again, so a confirmed plan can't change under the user. It runs only if the dataset and its contract are unchanged since the hold, and the plan passes the checks again; otherwise the user is asked to ask again (ADR013 §6.3).
    11. The harness reports answered right and correctly held separately, and an answer that needed one column choice separately from both. It gets a permanent held-out question set: paraphrases written by someone who has not read the code, graded by the same oracles. Hand-written vocabulary rules are capped (see ADR013 §5.1).
    12. Merge order: #102, then corpus formats and ZIP upload, then the held-out questions scored on main with and without the model (the baseline "rises" is measured against), then #107, then a re-run of make accept with and without the model. This list is the one place the order is kept.
    13. A governed SQL path for one table. The model writes SQL and it is checked against the contract. Small cells are suppressed in the output, and the SQL is shown.
    14. Done when model-written SQL answers the questions that the word-accounting gate would hold, on one table. #106 (user-typed SQL) is the validator and sandbox it runs in.
    15. Every combination of filters is checked within each answer, in each group, on both the question path and the SQL path. An answer's filters (its WHERE, FILTER and count_if terms, or the plan's filters) split each group into cells, one for each combination of filters a patient meets. If a cell holds 1–10 patients, that group's numbers are hidden. So dropping any set of filters, subtracting two filtered counts inside one answer, or a filter that removes few patients in one group can't reveal a small count. #106 checks only its whole WHERE, and each aggregate against its unfiltered group; this check goes further (ADR013 §4.5).
    16. Every answer shows the step-by-step patient count: "1,141 patients → 612 women → 341 with RRMS". A count is hidden when it would reveal a hidden cell, and complementary suppression hides others until no hidden cell is the difference of two shown counts. Hiding only a small step would fail, because the counts on either side give it away.
    17. The design for this step is cut down to what #106 built. See ADR013.
    18. Statistics as tools. The model picks the test, and the existing core computes it.
    19. MVP. Widen to the corpus: Sepsis 2019, the MIMIC demos, population sets with ranges, and patient-level sets across specialties. Compare local Ollama with a hosted stand-in. The bar is 0 WRONG and 0 LEAK.
    20. A dataset-version log of shown counts lands here. It refuses a count that differs from one already shown by a single changed filter.

    The design reference is ADR013. Take from it only what the current step needs.

    What waits

    These don't move the acceptance table, so they wait until a step needs them:

    • packaging and signed installers;
    • contract revisions and lineage;
    • charts;
    • encryption at rest (full-disk encryption covers it; see local data security).

    What privacy does not cover yet

    Within one answer, the check is designed but not built yet. Today the question path checks the patients its filters remove together, not each combination. #106's SQL path, off by default, does not compare two filtered counts in one answer: on its branch, count(*) FILTER (WHERE a = 1) - count(*) FILTER (WHERE a = 1 AND b = 1 AND c = 1) shows 5 patients. The check lands on the SQL path before that path can be on by default, and on the question path with step 4.

    Across answers, the check reads no earlier answers. It still covers two answers when one answer's filters include all of the other's and the groupings match, or the one with fewer filters is not grouped: every count the answer with fewer filters shows is a sum of cells the other answer checked. Other pairs can still be subtracted: for example, "patients over 65" and later "patients over 66", or the same filter grouped two different ways. Until the dataset-version log lands in step 6, the app does not detect this. After it lands, the log refuses a count one filter change away from a count already shown, and notes other overlaps; it cannot catch every combination of earlier questions.

    Mature systems have the same limit. DataSHIELD answers it with a warning, a session log and sanctions from a data custodian. This app has no custodian, so it promises only what its code enforces.

    Merge gate

    A change merges only if it moves the acceptance table, or fixes a WRONG, LEAK or ERROR that the table shows. Hardening for cases the corpus doesn't hit waits.

    Exception: fixes for privacy, security or data loss merge on their own merits, whether or not the corpus triggers the issue.

    Issues follow the table. Each reproducible WRONG, LEAK, ERROR or unacceptable HOLD gets a GitHub issue. One issue covers one cause and lists every question it affects. It links the PR that fixes it and the oracle the fix must pass.

    • An unacceptable HOLD is a hold on a question that expects an answer, when the hold gives the clinician nothing to act on, or when it happens on a held-out paraphrase.
    • Issues are labelled acceptance plus one grade label: grade:WRONG, grade:LEAK, grade:ERROR or grade:HOLD.

    What we borrow from other tools

    We adopt none of these; each needs a server, a database, a licence or a workflow that doesn't fit a local Polars app. We borrow their mechanisms.

    Tool What we borrow Where it lands
    Microsoft Data Formulator Clarify by choosing, not rephrasing: a hold offers columns to pick. Later, follow-ups that name the answer they build on. Step 3; step 6
    DataSHIELD Its subset rule (a filter must remove no one or enough people), made strict. Its model-saturation check (nfilter.glm). Step 4; step 5
    OHDSI ATLAS Inclusion-rule attrition: count every combination of filters, then show the step-by-step count (Book of OHDSI, ch. 10). Step 4
    jamovi and JASP Assumption checks, and a rank-based alternative next to each parametric test. Step 5
    ACRO A residual degrees-of-freedom floor for regressions, and dominance checks on sums and means. Steps 4–5

    Nearest competitor: Domino Clinical Data Explorer (Apache-2.0). A chat agent calls aggregate data tools, can run on a local Ollama, and never shows the model a hidden result. It has no small-cell suppression, and it is built to run on the Domino platform. This app's edge is small-cell control, grain, units and statistical refusals, not "local" alone. Re-check it at MVP.

    Real data

    Synthetic data is the rule. The only exception is acceptance testing on public, openly licensed, de-identified datasets: fetched at test time from their public source, checked against a pinned checksum, used under their licence, never committed, and never shown row by row. Aggregate results (counts, statistics, grades) may appear in logs, issues and pull requests. Everything else, unit tests included, uses synthetic data.

    The same rule appears in CONTRIBUTING.md and SECURITY.md.
