    Renderer design direction

    Status: adopted for the Electron renderer (electron/index.html, electron/src/index.css, electron/src/renderer.js and the panel modules). This page is the contract the CSS and the renderer implement. Values here are the source of truth; change them here first.

    The brief

    The owner asked for an app that feels like a conversation-first assistant, but for clinicians rather than programmers, with a dark mode, and with evidence-backed reasoning, always.

    We borrow interaction and layout patterns that conversation-first apps share: one centred reading column, a composer docked at the bottom, a left sidebar with past conversations titled by their first question, quiet chrome. We copy no product's name, logo, brand colours, icons or assets. The sage accent, the warm neutrals and the type pairing are this app's own.

    Four independent audits, each applying one designer's published skill set, were rendered in Playwright against the pre-redesign renderer (m2int). Their reports and screenshots live in the session scratchpad under design_audit/{mengto,owl,conardli,kowalski}. The skills are criteria, not authority: where they disagree, the decision below rests on measured evidence or on what a clinician has to do with the screen.

    Where they disagree, and what we chose

    Held card: amber left rule, or tinted card with a border?

    MengTo and Kowalski proposed an amber/accent left rule; ConardLi proposed a tinted card with a 1 px border and no stripe. Decision: tinted card + 1 px border, no stripe. Evidence: MengTo's own no-ai-design-slop checklist lists "a thick accent stripe is attached to one side of a rounded card" as a slop pattern (ARTICLE.md, line 88), so the stripe contradicts the skill that proposed it. Functionally, a left rule is also the shape of a quotation or a callout; a draft is better signalled by a different surface plus a heading that says what to do ("Check this plan before it runs"). The border passes 3:1 against its tint in both themes (3.51 light, 3.10 dark).

    Fonts: Source Serif 4 + Source Sans 3, or IBM Plex?

    MengTo ranked Source Serif 4 + Source Sans 3 first; ConardLi proposed IBM Plex Sans + Plex Mono. Decision: Source Sans 3 for all interface text and tables; Source Serif 4 only for the claim headline and the empty-state greeting. No mono face. Evidence: the audits agree the mono plan line and mono table are the problem, so a mono face has no remaining job. Source Serif was drawn as a companion to Source Sans, so the pair shares proportions and needs no tuning. Source Sans 3 ships tabular lining figures (tnum), which the right-aligned tables rely on. A serif headline gives the one sentence that matters a distinct voice from the interface around it, which is the "one authored moment" MengTo asks for. Both are SIL OFL 1.1 and were taken from Adobe's own repositories (see "Fonts and licences").

    Dark base: #121413, #161513 or #141412?

    Owl proposed a green-tinted #121413, ConardLi a warm #161513, Kowalski a neutral-warm #141412, MengTo #1B1A18. Decision: #161513 (warm). The light theme is a warm paper (#F7F6F3); a warm dark keeps the two themes the same app. A green-tinted base lowers the separation of the sage accent, which is the only hue that marks "act here". Elevation is shown by lightness steps (#161513 → #1B1A18 → #211F1D → #2C2A27), not shadows (Owl, ConardLi, Kowalski agree on that).

    Refused: blue "info", or neutral?

    Owl proposed blue (#33598a / #9db8e0); ConardLi a slate neutral; Kowalski "calm, not red". Decision: neutral. Uses the secondary text colour on the sidebar surface, with an info icon and the words "Not answered". A refusal on privacy grounds is the product working, so it must not borrow the error's red; a second accent hue (blue) would compete with sage, which already means "you can act". The word and icon carry the meaning (WCAG 1.4.1).

    User question: muted line or bubble?

    MengTo proposed the question as a small muted line above each answer; ConardLi a right-aligned bubble. Decision: right-aligned bubble on the sunken surface, max 80 % width. The chain a clinician audits is question → plan → answer. A muted line makes their own words look like metadata; the bubble keeps turn-taking legible when scanning back.

    Status pills on every message?

    Owl proposed "Answered ✓ / Needs your OK / Not answered / Error" pills on every message. Decision: label only the states that need different action (held, refused, error, stopped). An answer is shown by its claim; a pill saying "Answered" on every turn is noise (MengTo's restraint criterion). Answers get the analysis type ("Group comparison") as a caption.

    Hidden cells: "—", "hidden", or "<11"?

    MengTo proposed "—" with a footnote "fewer than 11 patients"; ConardLi "<11" with †; Owl a muted italic "hidden". Decision: muted italic "hidden" with a † and one footnote; cells that the API already sends as "<11" keep that text, muted, with the same †. Evidence: the API marks both primary small cells (1–10) and secondary cells (hidden so a small cell cannot be worked out from a total) with the same word, deliberately, so the two cannot be told apart (result_presentation.py, _mask). Rendering every hidden cell as "fewer than 11" would be false for secondary cells; rendering "—" reads as "missing" or "zero" in clinical tables. The footnote says what is true for both: "Hidden to protect privacy: counts from 1 to 10 are not shown, and some other cells are hidden so those counts can't be worked out from totals." Within one answer the API uses one marker: when the table hides a count, the claim does not write "<11" for it either. It says "n hidden" (n, the exclusions and any rows a filter removed add up to the dataset's row count, and n plus the exclusions is the filtered cohort a COUNT shows, so n is hidden when any of them is small, together with every group size; with n hidden the clause never mentions exclusions, even when their count is large enough to show: "n hidden; 50 excluded" would tell a small n apart from a small exclusion count, and "n=377; some excluded" would give the exclusions away to a second COUNT), "count hidden", or "Total count hidden." for a filtered count. The semantic layer sends the rows the filters removed (n_filtered_out, counted where compute filtered them, in the unit of the total: patients for a distinct-patient count), so the presenter never works it out per analysis type. A statistic that can be one patient's value (a mean, a median, min and max, a group's mean or median) is shown only when the count beside it is present, is a whole number and is not hidden. If the count is missing or is text or a decimal, the statistic is hidden as well, and the claim says "Statistics for ldl are not shown because n is missing." or "Median time to death (days) is not shown because n is missing." A table cell that should be a count but is not a whole number is hidden like a small count. "<11" appears only when it is the answer's sole hidden count, e.g. "Total count: <11." We never write "<5"; the threshold is 11. Only the API's exact tokens mean hidden: the lowercase suppressed and <11 (built from the threshold). Any other text, such as an age band "<65" or a category spelled "Suppressed", is a label and is shown as written, with no † and no footnote.

    Data check (cohort details) uses one label only. Its report (contracts/quality.py) shows every suppressed count the same way, as "some … ; count hidden to protect privacy", never "<11": with a visible row total, two labels would tell a reader that the non-"<11" hidden counts are 11 or more, and a column's missing + bad + valid counts would then pin a small one. A hidden count there only means "at least 1" (zero is shown as 0). A check whose count is hidden always has the status "review", whatever the value (a pass/warning would say which side of a threshold it is on: 1 of 20 missing "passed" at 5% meant exactly 1), so the summary and "N things to review" depend only on shown numbers. When any count in a column is 1–10, all of that column's non-zero counts are hidden together (hiding only some would let a reader work out which was smaller). A column gets one problem-value check at most: a coded column whose name looks like "age" or "BMI" gets its codebook check, not a range (codes are not measurements). The row count is always shown, as in the meta line and the first-rows overview; tables of 1–12 rows show it but hide every column count, zeros included, with the line "{N} rows: too few rows to report counts". Its footnote: "Hidden to protect privacy: counts from 1 to 10 are not shown, and some larger counts are hidden too so those can't be worked out from the totals. A hidden count is never zero."

    Session titles

    All audits ask for sessions titled by their first question. The API does not persist messages (message_count is always 0 for real sessions; conversation history is in memory), so there is no first question to show after a restart. Decision: sessions created in this run are titled by their first question (held in memory only); others read "Earlier conversation". The renderer also reads a title field if the API ever sends one. We rejected saving question text in localStorage: questions can identify patients, and a copy there would survive "Delete dataset", which promises to remove every session for that dataset (docs/security/LOCAL_DATA_SECURITY.md). Follow-up for the API: persist the first question with the session so deleting the dataset deletes it too.

    Space, radius, elevation

    • Spacing: 4, 8, 12, 16, 24, 32, 48, 64 (--sp-1 … --sp-8). Nothing off this ladder.
    • Radii: 6 controls, 10 cards/tables/panels, 16 composer, full for chips.
    • Elevation: light uses --shadow-1 on the composer and --shadow-2 on menus/sheets; dark uses no shadows, only a lighter surface plus a 1 px border.
    • Layout: sidebar 264 px; chat column max 760 px with 24 px side padding; dataset panel 440 px sheet from the right. Under 1000 px wide the sidebar narrows to 232 px; the column stays fluid. Under 700 CSS px (the 800 × 600 minimum window at 200% zoom is 400 px wide) the sidebar folds behind a "Cohort and conversations" toggle (aria-expanded). The open drawer is not modal: its close button and Escape return focus to the toggle; a click outside it or focus moving out of it closes it; its scroll is contained. The language model banner can be dismissed so the composer stays on screen; the offline banner cannot, because its "Try again" is the only way to reconnect. The composer shows the same 2 px --focus-ring outline as every other control on :focus-within.

    Motion (after Kowalski)

    Token Value
    --ease-out cubic-bezier(.23, 1, .32, 1)
    --ease-in-out cubic-bezier(.77, 0, .175, 1)
    --dur-press 100 ms
    --dur-hover 120 ms
    --dur-pop 180 ms
    --dur-enter 220 ms
    --dur-exit 140 ms
    --press-scale .97

    Choreography: - Send: button presses to scale(.97) (transform only). The question bubble enters at once (opacity + 4 px rise, 180 ms). - Working: three dots pulse opacity on a 1.2 s cycle; the stage text ("Reading your question", "Running the analysis") is a sibling, static, and swaps text without moving. After 3 s an elapsed counter appears. - Answer lands: the card enters with opacity 0→1, translateY(6px)→0, blur(2px)→0 over 220 ms; caption, claim, stats and table stagger by 40–60 ms. Numbers never count up. - Held card: same entry. After "Run this analysis" the plan stays and the result arrives below; after "Not what I meant" the buttons are replaced by a one-line note. - Scroll: when the reader was at the bottom, a new answer is scrolled into view; if the answer is taller than the view, its top is aligned instead so the headline is never off-screen. - Hover effects are gated behind (hover: hover). Transitions name their properties (no transition: all). - Reduced motion: no translate, no blur, no pulse; opacity fades of 150 ms remain, scroll is instant.

    Theme

    • Three choices: System, Light, Dark, as a segmented radio group in the sidebar footer.
    • Electron: the renderer calls window.appTheme.set(source) (preload → ipcMain.handle), main sets nativeTheme.themeSource, which drives prefers-color-scheme in the page, and persists the choice to settings.json in the app's user-data folder. Main reads it before the window is created and sets the window backgroundColor to match, so the first frame is already the right theme. Only the app's own page may call it, and only these three values are accepted. Main also passes the saved choice to preload (--ca-theme=<source>), exposed as appTheme.initial, and the <head> script uses it first, so a stale localStorage copy can never paint the other theme.
    • Browser (Vite, Playwright): an inline script in <head> reads localStorage (wrapped in try) and sets data-theme before first paint; the stylesheet does the rest.
    • Theme change cross-fades background and text colours for 200 ms (none under reduced motion).

    Navigation

    • Sidebar (top to bottom): app name; cohort switcher (native <select>, so keyboard and screen readers work as before) with a ⋯ button opening a small menu: Upload a file, Use the sample cohort, Preview and details, Refresh the list, Delete this cohort; a meta line "400 rows · 14 variables" (rows, not "patients": a file can hold several rows per patient, and the meta line must not claim what it has not checked); a "New question" button; past conversations grouped by Today / Yesterday / Previous 7 days / Older; footer with the on-this-computer status and the theme switch.
    • Main: the chat column and the docked composer only. An offline banner appears only when the engine cannot be reached; the "Backend connected" badge is gone.
    • Dataset panel: a sheet from the right with the preview table, variable suggestions and change history. Opened from the ⋯ menu or the meta line; Escape or the close button returns focus to where it came from.

    Known limits

    • Session titles after a restart need the API to persist the first question (see above).
    • Earlier answers in a resumed session are not shown: the API has no transcript endpoint.
    • The confirm request is built in one function (buildConfirmRequest in electron/src/confirmHold.js) so a server-issued hold token can be added in one place.
