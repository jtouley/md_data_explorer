    ADR010: Migration from Streamlit to Lightweight Web UI

    Status: Proposed Date: 2026-01-03 Decision Makers: Engineering Team Related ADRs: ADR001 (Multi-table support), ADR009 (LLM-Enhanced UX)

    Context

    The clinical analytics platform currently uses Streamlit as its UI framework. While Streamlit enabled rapid prototyping and quick iteration during MVP development, several limitations have emerged as the platform has matured:

    Current Pain Points

    1. State Management Fragility
    2. st.session_state acts as a mini state machine with no validation
    3. State persists incorrectly across dataset changes causing UI bugs
    4. No type safety or schema validation for session state

    5. Documented in Ask_Questions.py lines 1584-1610 as known fragility

    6. Performance Constraints

    7. Full page reruns on every interaction (st.rerun())
    8. No incremental rendering or DOM diffing
    9. Heavy widget rendering overhead for large chat transcripts

    10. @st.cache_resource required for non-picklable objects (DuckDB/Ibis)

    11. User Experience Limitations

    12. No session history browsing or search
    13. Cannot open multiple conversations in tabs
    14. No dark mode support
    15. Poor mobile responsiveness

    16. Chat interface lacks modern UX patterns (collapsible sections, streaming indicators)

    17. Development Constraints

    18. Limited testability (widget state difficult to mock)
    19. No component reusability outside Streamlit
    20. Difficult to add custom interactions or animations

    21. Streamlit updates can break UI (version coupling)

    22. Deployment Complexity

    23. Streamlit server required for hosting
    24. No static site generation or CDN deployment
    25. Difficult to scale horizontally (session affinity required)
    26. No API-first architecture for future mobile/CLI clients

    Trigger for Change

    Recent features (LLM-enhanced UX in ADR009, multi-table support in ADR001) have pushed Streamlit to its limits: - Chat transcript management requires complex state machine logic - Result caching uses custom LRU eviction to work around Streamlit limitations - Variable selection UI requires careful rerun orchestration - Trust UI (patient-level export) needs custom download handling

    The platform has outgrown Streamlit's rapid prototyping strengths and now needs production-grade UI architecture.

    Decision

    We will migrate from Streamlit to a FastAPI backend + Next.js frontend architecture with the following characteristics:

    Key Design Decisions

    1. Backend: FastAPI
    2. Rationale: Python-based (reuse existing logic), async support, OpenAPI docs, SSE support
    3. Alternatives considered: Flask (no async), Django (too heavy)

    4. Trade-offs: New dependency, but gains API-first architecture

    5. Frontend: Next.js

    6. Rationale: React ecosystem, TypeScript support, excellent DX, App Router for modern patterns
    7. Alternatives considered: Vanilla React (more setup), SvelteKit (different ecosystem)

    8. Trade-offs: Adds Node.js toolchain, but gains modern UI capabilities

    9. State Management: Server-Side Sessions

    10. Rationale: Avoid Streamlit's fragile session_state, enable multi-tab browsing
    11. Implementation: SQLite for MVP (easy migration to Postgres later)

    12. Trade-offs: Database dependency, but gains persistence and reliability

    13. Real-Time Updates: SSE (Server-Sent Events)

    14. Rationale: One-way streaming (server → client), simpler than WebSockets for this use case
    15. Usage: Stream query execution progress, intermediate results

    16. Trade-offs: No client→server streaming, but sufficient for current needs

    17. Styling: TailwindCSS

    18. Rationale: Utility-first, dark mode support, responsive out of box
    19. Alternatives considered: Styled Components (more verbose)

    20. Trade-offs: Learning curve, but gains rapid UI development

    21. Plotting: Backend Data + Frontend Rendering

    22. Rationale: Separation of concerns, responsive rendering, no image bandwidth
    23. Implementation:
      • Backend generates plot data as JSON (e.g., {time: [], survival: [], ci_lower: [], ci_upper: []})
      • Frontend renders with Recharts (LineChart for survival, custom heatmap component)
    24. Alternatives considered: Backend PNG generation (poor UX), client-side matplotlib (not possible)

    25. Trade-offs: More frontend code, but gains interactivity and responsiveness

    26. Caching: Redis (production) + in-memory (dev)

    27. Rationale: Result cache needs TTL, LRU eviction, persistence
    28. Implementation: FastAPI dependency injection, async access
    29. Trade-offs: External service dependency (production), but gains scalability

    What Changes

    New Components: - FastAPI application with routes, services, models, DB layer - Next.js web application with React components - SQLite database for session persistence - Alembic migrations for schema management - Jest + Playwright test suites for frontend - Makefile targets: make dev-web, make dev-api, make test-web, make test-e2e

    Extracted and Reused: - components/question_engine.py → api/services/query_service.py (wraps existing logic) - components/result_interpreter.py → api/services/interpretation_service.py - Session state logic → api/services/conversation_manager.py - Result caching logic → api/services/result_cache.py - All core/ modules (semantic layer, NL engine) → used directly via FastAPI dependency injection - All analysis/ modules (stats, survival) → used directly

    Deprecated: - ui/app.py and all ui/pages/*.py → archived to archive/streamlit_ui/ - Streamlit-specific components → ported to React components - @st.cache_resource patterns → replaced with FastAPI Depends() - st.session_state → replaced with SQLite-backed sessions

    Unchanged: - All business logic in core/ and analysis/ modules - Data processing (Polars, DuckDB, Ibis) - LLM integration (Ollama, Claude) - Dataset definitions and loaders - Test fixtures in tests/conftest.py (reused for API tests)

    Migration Strategy

    Phase 1: Parallel Development (Weeks 1-2) - Build FastAPI backend alongside existing Streamlit UI - Extract ConversationManager, ResultCache from session_state logic - No user impact (Streamlit still runs)

    Phase 2: Feature Parity (Weeks 2-4) - Port all 8 pages to Next.js components - Implement all 6 analysis type renderers - Add Trust UI, follow-up suggestions, variable mapping - Internal testing with feature flag

    Phase 3: Cutover (Week 4) - Deploy with ENABLE_NEW_UI=true feature flag - Monitor for critical bugs (rollback if >3 in 48h) - Archive Streamlit code to archive/streamlit_ui/

    Phase 4: Cleanup (Week 5) - Remove Streamlit dependencies from pyproject.toml - Update documentation (README, setup guides) - Remove feature flag after stabilization

    Rollback Plan

    • Trigger: >3 critical bugs within 48h of cutover
    • Process:
    • Set ENABLE_NEW_UI=false (reverts to Streamlit)
    • Investigate and fix issues
    • Re-deploy new UI when ready
    • Data safety: Sessions stored in SQLite during new UI, read-only access to Streamlit session files

    Consequences

    Positive

    1. Better Performance
    2. Incremental rendering (React diffing)
    3. No full-page reruns
    4. Static asset optimization (Next.js)

    5. API caching with React Query

    6. Improved User Experience

    7. Session history browsing and search (like claude-run)
    8. Multi-tab support (no session affinity issues)
    9. Dark mode
    10. Mobile-responsive design

    11. Modern chat UX (collapsible sections, streaming indicators)

    12. Enhanced Testability

    13. API contracts testable in isolation (FastAPI TestClient)
    14. Frontend components testable with Jest + React Testing Library
    15. E2E flows testable with Playwright

    16. Better separation of concerns (UI vs business logic)

    17. Future-Proof Architecture

    18. API-first enables future mobile/CLI clients
    19. TypeScript types auto-generated from OpenAPI schema
    20. Component reusability across potential future products

    21. Easier to add features (no Streamlit limitations)

    22. Developer Experience

    23. Hot module replacement (Next.js dev server)
    24. Better IDE support (TypeScript)
    25. Modern debugging tools (React DevTools)
    26. Clearer separation of concerns

    Negative

    1. Increased Complexity
    2. Two codebases (backend + frontend) vs one Streamlit app
    3. Node.js toolchain added (npm/pnpm, TypeScript, build process)

    4. More deployment moving parts (API server + static site)

    5. Learning Curve

    6. Team needs React/Next.js knowledge (currently Python-focused)
    7. Frontend testing patterns (Jest/Playwright) different from pytest

    8. SSE debugging more complex than Streamlit reruns

    9. Development Velocity Impact

    10. Initial slowdown during migration (4-5 weeks estimated)
    11. Two-sided changes required (API + frontend) for new features

    12. More boilerplate for simple features

    13. Operational Overhead

    14. Database required (SQLite for dev, Postgres for production)
    15. Redis for caching (production)
    16. More services to monitor and maintain

    Mitigation Strategies

    1. Complexity: Use claude-run as reference implementation, follow established patterns
    2. Learning curve: Pair programming sessions, code reviews, documentation
    3. Velocity: Keep Streamlit code in archive for reference during migration
    4. Operations: Start with SQLite (file-based, no extra service), migrate to Postgres/Redis only when needed

    Implementation Plan

    Detailed 60-step implementation plan with TDD workflow: .cursor/plans/streamlit_to_lightweight_ui_refactor_4iMKv.plan.md

    Critical Path

    1. Phase 1.5: Verify semantic layer compatibility with FastAPI (DuckDB async, Ibis dependency injection)
    2. Phase 2-4: Build backend API (session, dataset, query endpoints) with TDD
    3. Phase 5-6: Build frontend components (conversation list, chat, renderers) with Jest tests
    4. Phase 7: Upload flow and variable mapping wizard
    5. Phase 8: Integration testing (end-to-end flows)
    6. Phase 9: Deployment and documentation

    Success Criteria

    1. ✅ All 8 Streamlit pages ported to new UI
    2. ✅ All 6 analysis types working (DESCRIBE, COMPARE_GROUPS, FIND_PREDICTORS, EXAMINE_SURVIVAL, EXPLORE_RELATIONSHIPS, COUNT)
    3. ✅ Session persistence and browsing (search, filter by dataset/date)
    4. ✅ Real-time SSE streaming for query execution with progress indicators
    5. ✅ Dark mode support with theme persistence
    6. ✅ All existing tests passing + new API/frontend tests
    7. ✅ Documentation updated (README, setup guides, architecture diagrams)
    8. ✅ Performance >= Streamlit (faster page loads, no reruns, <500ms API latency for simple queries)

    Quality Gates

    • Phase 2 Done: All API routes return 200/201, OpenAPI docs generated, unit tests pass
    • Phase 5 Done: All components render without errors, basic interaction tests pass
    • Phase 8 Done: End-to-end flow (upload → query → results → export) works, integration tests pass
    • Final Gate: make check-fast passes (backend + frontend tests), type-check clean, no new lint errors

    Risks and Open Questions

    Risks

    1. Risk: Semantic layer (DuckDB/Ibis) incompatible with FastAPI async patterns
    2. Likelihood: Medium
    3. Impact: High (blocks entire migration)

    4. Mitigation: Phase 1.5 explicitly tests this compatibility before building API routes

    5. Risk: Users expect conversation history to persist across migration

    6. Likelihood: High
    7. Impact: Medium (UX disappointment)

    8. Mitigation: Document clearly: "Migration launches with empty history, existing Streamlit sessions archived read-only"

    9. Risk: Plotting migration (matplotlib → Recharts) reveals edge cases

    10. Likelihood: Medium
    11. Impact: Medium (feature gaps)

    12. Mitigation: Explicit plotting strategy documented in Key Design Decisions

    13. Risk: Timeline underestimated (19-28 days → could be 35-40 days)

    14. Likelihood: Medium
    15. Impact: Low (not blocking, just slower)
    16. Mitigation: Phased rollout allows incremental delivery

    Open Questions

    1. Q: Should session migration be required or optional?

    2. A: Optional for MVP, document as "clean slate" launch

    3. Q: Deploy both UIs during transition or hard cutover?

    4. A: Feature flag deployment (ENABLE_NEW_UI env var) for safe rollback

    5. Q: Use Redis for caching in dev or only production?

    6. A: In-memory dict for dev (simpler), Redis for production (scalable)

    7. Q: Generate TypeScript types from Pydantic models or manually maintain?

    8. A: Auto-generate from OpenAPI schema (todo #14.5)
